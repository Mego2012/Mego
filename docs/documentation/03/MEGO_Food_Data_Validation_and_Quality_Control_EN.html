Purpose and scope

This document lists every quality-control layer that protects MEGO's food data: hard validation that rejects impossible values, the energy plausibility check, the import audit, flags carried from USDA, the Hub comparison, barcode validation, the read-only Data check in Settings (record counts, per-serving suspect foods, possible duplicates) and the recipe nutrition audit (docs/RECIPE-AUDIT.md). The guiding rule in all layers: values are flagged, never silently changed or invented. Sources: src/lib/nutrition.ts, src/lib/repo.ts, src/lib/sheetImport.ts, scripts/build-food-db.mjs, src/lib/sync.ts, src/lib/barcode.ts, src/lib/dataCheck.ts, scripts/recipe-audit.mts, src/pages/Foods.tsx, src/pages/Settings.tsx.

2. Hard validation (values that are rejected)

validateMacros() runs in createFood, updateFood and the personal-foods JSON import. Any error refuses the save ("Invalid nutrition values: …").

CodeRule (per 100 g)
<key>:nankcal, protein, carbs, fat missing or not a finite number (optional nutrients may be absent)
<key>:negativeany value below 0
macros:over100gprotein + carbs + fat > 100.5 g
fiber:overCarbsfibre > carbs + 0.5 (when carbs > 0)
sugar:overCarbssugar > carbs + 0.5
kcal:over900kcal > 900.5 (pure fat is ≈ 900 kcal/100 g)

Example: 950 kcal, P 60, C 30, F 20, fibre 40 → macros:over100g (110 g), fiber:overCarbs, kcal:over900. A name (Arabic or English) is also required.

3. Energy plausibility check

kcal is compared with 4P + 4C + 9F. Differences under 5 % or 8 kcal are ignored; larger ones are explained as fibre, nuts or animal food where the pattern fits; otherwise the food is "suspicious" when the reason is review, |pct| ≥ 10 % and |diff| ≥ 10 kcal. Full rules and worked examples: MEGO_Calorie_and_Macronutrient_Calculation_Methodology §6. The food editor shows the calculated value and the explanation live; the Foods page "Issues" card counts suspicious foods.

Observation: the issue label reads "Calories don't match macros (>15%)", while the code threshold is ≥ 10 % (plus ≥ 10 kcal and no fibre/nuts/animal explanation). The label text is therefore stricter than the rule actually applied; recorded for the owner (no code change made).

The audit also tallies states (raw / cooked / other), state labels and categories. Before every confirmed import a local pre-import backup is saved.

5. Incomplete foods

A food whose four main values are all 0 is incomplete (isIncompleteMacros); an imported food with missing values is also marked incomplete. Logging it throws INCOMPLETE_FOOD, recipes treat it as not available, and the Foods "Issues" card counts it. The fix is to edit the food and enter the label values.

6. Source flags (USDA, Open Food Facts, notes)

  • USDA: the build script flags (does not change) rows where kcal > 40 and |4P+4C+9F − kcal| ÷ kcal > 25 % — 211 of 12,879 rows. When such a food is copied into a user's list, its note ends with "⚠ calories vs macros differ in the source data".
  • Open Food Facts: community data; saved with the note "Open Food Facts — external data, verify with label"; text-search results without kcal, protein, carbs and fat are dropped.
  • Hub verification column: Food_Database carries a verification value (verified-usda / estimated / unverified / user). Notes containing the markers in §4 are treated as estimated: recipes using such a food are labelled as estimates.

7. Hub comparison and barcode validation

Hub: before importing the Hub's foods the app compares them with the phone (by Arabic name + state; kcal, protein, carbs, fat and piece weight). Any difference stops the flow until the owner accepts the Hub values; foods only in the Hub or only on the phone are listed.

Barcode: EAN-8, EAN-13 (also 12- and 14-digit) codes must pass the check digit. Example 4006381333931: weighted sum of the first 12 digits from the right (×3, ×1, …) = 89 → (10 − 9) mod 10 = 1 = last digit → valid.

8. Data check in Settings

Settings → Data check → Run check (runDataCheck). "Read-only check of the records on this device; nothing is changed." It reports:

  1. Record counts: food log entries and logged days, first–last logged day, weigh-ins / waist measurements, foods / my recipes, calorie targets (training / rest), latest pre-update backup (date, release, entries).
  2. Integrity vs the pre-update backup (one is saved per release, currently 1.3-training): intact when entries, body records, day logs and foods are each ≥ the counts in that backup; otherwise "Some tables have fewer records than the pre-update backup — open Local backups to review". Without such a backup the result is "No pre-update backup on this device yet".
  3. Per-serving suspect foods (suspectPerServing): name or category matches protein powder words (واي, whey, بروتين سكوب/مسحوق, protein powder, isolate, كازين, casein) AND 0 < kcal per 100 g < 250. A protein powder is about 350–420 kcal per 100 g, so a lower value almost certainly means per-scoop values were typed as per 100 g. The report names the food, its kcal and protein, and how many diary entries, own recipes and library recipes use it. Example: 120 kcal / 24 g protein → flagged; USDA whey powder 352 kcal / 78.13 g → not flagged. The owner does not use whey; the flag is informational only.
  4. Possible duplicates: diary items with the same date, meal, name (case-insensitive) and rounded grams, and own foods with the same name — see MEGO_Missing_and_Duplicate_Foods_Management. Nothing is removed.

9. Recipe nutrition audit

scripts/recipe-audit.mts (run with npx tsx scripts/recipe-audit.mts) computes all library recipes from USDA references only (what a new account sees) and, when the owner's private food table is present locally (tests/private, never committed), from the owner's values too. It writes docs/RECIPE-AUDIT.md. Checks per recipe: missing ingredients; per-serving kcal vs 4P+4C+9F differing by > 15 %; kcal per serving < 80 or > 1,300; owner-table vs USDA result differing by > 15 %; recipes containing whey.

Audit of 2026-11-10: 101 recipes, 100 fully resolved; unresolved ingredient: labneh (لبنة) — never estimated; 68 hand-checked USDA references; 6 flagged recipes:

10. Owner's review procedure

  1. After each release: run Data check on the main device and confirm "All records are intact".
  2. Open any per-serving suspect food, compare with the package label, and correct the value per 100 g (the food editor can convert from "per serving").
  3. Review the Foods page "Issues" counts (no values, calorie mismatch, flagged in notes) and fix or confirm each food.
  4. Before a Hub import, resolve differences shown by the comparison.
  5. After changing recipe data or USDA references, re-run the recipe audit and review the flags.
