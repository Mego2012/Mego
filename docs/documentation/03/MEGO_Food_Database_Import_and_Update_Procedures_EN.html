Purpose and scope

This document gives the step-by-step procedures for bringing food data into MEGO and for updating it safely: rebuilding the USDA reference database, pulling the owner's Google Sheets Hub (Food_Database tab), importing CSV/Excel files, exporting/importing personal foods (JSON), adding foods from USDA search, Open Food Facts and barcodes, and approving recipe ingredient matches, completing the food database from the recipe library and filling missing Arabic/English names. It also explains how updates are recorded (change history, versions) and what is never done (deleting foods, converting raw↔cooked, inventing values). Sources: scripts/build-food-db.mjs, src/lib/sheetImport.ts, src/lib/sync.ts, src/lib/customFoods.ts, src/lib/refFoods.ts, src/lib/barcode.ts, src/lib/repo.ts, src/lib/recipeEngine.ts, src/lib/libraryFoods.ts, src/lib/foodNames.ts, src/pages/Foods.tsx, scripts/laptop-setup.mjs, apps-script/Code.gs, src/pages/Settings.tsx, docs/HUB.md.

General rules applied by every procedure: values are copied as published (per 100 g); imports never delete foods; diary entries keep their own snapshot so past days do not change; raw and cooked are separate records and never converted.

2. Procedure A — rebuild the USDA reference database

Current build: meta.builtAt 2026-11-06; SR Legacy (release 2018-04) 7,448 foods + FNDDS Survey foods (release 2024-10-31) 5,431 foods = 12,879; 195 categories; 1 food skipped (no energy or macros); 211 rows energy-flagged.

  1. Download the USDA FoodData Central CSV releases for SR Legacy and FNDDS (Survey) and unzip them into one folder. The script looks for sub-folders whose names contain sr_legacy_food_csv and survey_food_csv and that contain food.csv. (The exact download location/release names are Not verified in the repository.)
  2. Run node scripts/build-food-db.mjs <folder>. It writes public/fooddb/usda.json and public/fooddb/usda-extra.json and prints the stats.
  3. Check the printed stats against the previous build (counts, skipped, energyFlagged).
  4. Run the unit tests (npx vitest run). They check, among others: 12,879 foods with sources and valid numbers, spot values copied exactly (tests/fooddb.test.ts), every Food Intelligence catalog id exists (tests/intel.test.ts), every recipe USDA id exists (tests/cardio-goals.test.ts). If USDA changed a count or removed an id, update the test expectation or the mapping deliberately.
  5. Commit and deploy through the normal release (MEGO_Build_and_Release_Procedures). The service worker precaches fooddb/usda.json and caches usda-extra.json stale-while-revalidate, so users receive the new file with the app update.

What the script does: reads energy (nutrient 1008, falling back to Atwater-specific 2048 then general 2047), protein 1003, fat 1004, carbs 1005, fibre 1079, sugars 2000 (fallback 1063), saturated fat 1258, sodium 1093; up to 6 portions per food; excludes SR categories "Quality Control Materials" and "Baby Foods"; skips foods without energy or any of the three macros; rounds to 0.01; flags (does not change) rows where kcal > 40 and |4P+4C+9F − kcal| ÷ kcal > 25 %. IDs are prefixed S (SR Legacy) or N (FNDDS) + FDC ID.

Effect on users: foods already copied into a user's list (source usda) keep their values; the new reference values apply only to foods picked afterwards. Re-checking previously copied foods is a manual task (Not automated).

3. Procedure B — import foods from the Google Sheets Hub

Available on the owner's device after connecting the backend (Settings → Sync). The backend action foods returns the Food_Database tab.

  1. Connect / Save + Test connection. The app tests the backend, then runs a read-only comparison (checkHubFoods): foods identical, values different, only in Hub, only on phone (matched by Arabic name + state).
  2. If any value differs, the flow stops and lists up to 10 differences as "local kcal/P/C/F → Hub kcal/P/C/F". Nothing is overwritten until the owner presses Use the Hub values (backup first; past diary entries keep their values).
  3. Before importing, a local backup pre-import is saved.
  4. pullFoodsFromSheet() parses the tab and merges it with importParsedFoods(…, 'sheet'); the message reads "Imported: {added} new, {updated} updated, {unchanged} unchanged. Nothing was deleted."
  5. Later updates: press Import foods from sheet in Settings → Sync.

Structured Food_Database columns (required: food_id, name_ar, kcal_100g, protein_100g, carbs_100g, fat_100g; optional: name_en, category, fiber_100g, sugar_100g, sodium_mg_100g, piece_g, state, state_label, prep, notes, verification, active). Rows with active = no or without food_id are skipped. A missing required column stops the import with missingColumns:….

Write-back: with "Write food edits back to the Google Sheet (backs up the tab first)" enabled, edits of sheet foods are sent with the saveFoods action to Food_Database (never to the original tab). Personal (non-sheet) foods are pushed as ordinary records.

4. Procedure C — import a CSV or Excel file

  1. Foods → Import / export → Import CSV / Excel (.csv, .xlsx, .xls).
  2. Excel: sheets named "قاعدة بيانات الأطعمة", "Foods" or "Food Database" are tried first, then the others; the first sheet with a recognisable header is used.
  3. Header detection: within the first 15 rows, the first row that has a name, a calories and a protein column (Arabic or English names, e.g. "الاسم/name", "سعرات/kcal", "بروتين/protein"). Other recognised columns: English name, category, carbs, fat, fibre, sugar, sodium, piece weight, state, preparation, notes.
  4. The Import preview shows totals (raw / cooked / other) and issue counts (no values, missing values, decimal comma, energy mismatch, duplicate name, flagged in notes) and lists up to 60 rows with issues and their row numbers.
  5. Press Import: a local backup pre-import is saved, then rows are merged (origin file).

4.2 Merge rules (importParsedFoods)

  • Each row has a key: the Hub food_id (structured tab) or the Arabic name (file); a repeated name gets name#2, name#3…
  • Existing food with the same key → updated only if a tracked field changed; otherwise "unchanged".
  • Foods imported earlier by name are re-keyed to the new stable ID instead of duplicated (legacyKey).
  • A name-keyed row matches an existing Hub food (ID F0001…) with the same Arabic name and state, so a file never duplicates Hub foods.
  • No match → new food with source = sheet. Foods not present in the file are kept (counted as "kept").

5. Procedure D — export / import personal foods (JSON)

  1. Foods → Export my foods (JSON) saves mego-my-foods.json (format mego-custom-foods, version 1) with all non-archived foods whose source is not sheet; ids, counters and timestamps are removed.
  2. Foods → Import my foods (JSON) on another device/account: each food is validated (validateMacros, a name, state raw/cooked/other). Invalid → counted "invalid"; same name + state already present → "skipped"; otherwise added. The source is kept if usda or openfoodfacts, else set to custom.

6. Procedure E — add single foods

  • USDA search (Add food / food picker): picking a reference food copies it once into the user's foods (source usda, sourceRef "USDA FDC <id> (…)", USDA portions as servings); later picks reuse that copy. If USDA flagged the energy, the note says "⚠ calories vs macros differ in the source data".
  • Barcode: EAN-8/EAN-13/UPC-A check digit validated; a local food with that barcode is used first; otherwise Open Food Facts is queried. The product form is editable; saved with source openfoodfacts and the note "Open Food Facts — external data, verify with label" (or custom if the user typed the values).
  • Open Food Facts text search: only products with kcal, protein, carbs and fat are listed.
  • From a label: "Create “…” as my food" in the picker opens the food editor with the search text as name. Values may be typed per 100 g, per 100 ml (÷ density) or per serving (× 100 ÷ serving grams); they are stored per 100 g.

7. Procedure F — recipe library foods and bilingual names

7.1 Approve recipe ingredient matches

Library recipes may use hand-checked USDA matches for ingredients that are not in the user's foods. Saving the recipe to "My recipes" (or logging it) approves them: approveRecipeMatches adds each matched USDA food once, under the recipe's Arabic ingredient name, with note "… · approved recipe match". Existing foods are never changed; ingredients without a reliable match (e.g. labneh) are not added (see MEGO_Missing_and_Duplicate_Foods_Management).

7.2 "Complete my food database" (Foods page, libraryFoods.ts)

  1. Foods → card Complete my food database → Check what is missing. A read-only preview (previewLibraryFoods) counts: ingredients to add, ingredients already in my foods, ready meals to add, meals already in my foods, and lists ingredients with no verified values.
  2. Add to my foods (completeFoodDatabase): a local backup pre-import is saved first (only if something will be added); then (a) every recipe-library ingredient that has no food of that Arabic name is added from its USDA match (same mechanism as 7.1), with the short English name from the name dictionary when known; (b) every library recipe whose ingredients are all known becomes a ready food: category "وجبات (مكتبة الوصفات)", state cooked, source custom, sourceRef "MEGO recipe library: <id>", one serving "حصة (وصفة)" = raw ingredient grams per serving.
  3. Adds only: existing foods (same Arabic name or same sourceRef) are never changed. Recipes needing a missing ingredient are skipped.

Result on a new, empty account (computed 10 Nov 2026): 68 ingredients to add, 1 missing (labneh / لبنة), 100 ready meals to add, 1 skipped (lib-labneh-plate).

Ready-meal values: per 100 g = recipe totals × 100 ÷ total raw ingredient grams
Example "Pepper & tomato shakshuka" (2 servings, 940 g raw ingredients):
  per 100 g = 89.06 kcal · P 6.08 · C 8.15 · F 3.63
  1 serving = 470 g → 418 kcal · P 28.5 · C 38.3 · F 17.0   (log it by serving; seasonings ~8 kcal/serving not counted)

7.3 Fill missing Arabic / English names (foodNames.ts)

Foods → card Arabic & English names: shows foods with both names, names that can be added now, and foods still missing a name. Add the missing names saves a local backup, then fills only an empty English (or Arabic) name from the hand-translated dictionary public/fooddb/food-names.json (160 Arabic→English pairs, no nutrition values). Each food is re-checked just before writing; a name the user already has is never changed; if the new name would duplicate another food the food is left as is. Remaining foods must be named by hand in the food editor.

7.4 Same completion on the owner's Hub

Command (owner's laptop): node scripts/laptop-setup.mjs --hub-complete-foods. It updates the backend, requires backend version 8 or newer and the structured Food_Database tab, then:

  • adds every recipe-library ingredient missing from Food_Database with its USDA values (food_id LIB-ING-…, category "مكوّنات الوصفات"); ingredients without a verified reference are listed, never estimated;
  • adds every library meal not yet present as a ready food (food_id LIB-<recipe id>) computed from the Hub's own values (USDA only where the Hub had nothing), per 100 g of raw ingredients, piece weight = one serving; meals with an unusable ingredient are skipped;
  • calls the backend action fillFoodNames, which fills only empty name_en cells (after the once-per-day Drive backup).

Existing rows and values are never changed; the reference data comes from public/fooddb/library-recipes.json. Verified on the emulated Google backend with the real Code.gs: e2e/hub-complete-test.mjs 9/9 (including a second run that adds nothing). Running it against the live Hub: Not verified in this document.

8. How updates are recorded

  • updateFood compares tracked fields (Arabic/English name, category, per-100 g values, state, state label, preparation, notes, piece weight, density, servings). If any changed, version increases by 1 and a change-history row is written (action update from the app, sheet-update from Hub/file) with before/after values. Food editor → Change history tab shows it.
  • Creation logs create (or import for sheet foods); archive/restore are logged too.
  • Every change is queued for sync (outbox) and therefore reaches the cloud/Hub copy when sync is configured.
Example: the Hub changes "F0042" protein from 9.0 to 9.5
  pull → key F0042 found → per100 differs → updateFood(…, 'sheet')
  → version 3 → 4, history: before {per100:{…protein:9.0}} after {per100:{…protein:9.5}}
  → diary entries logged before keep protein 9.0 in their snapshot
