Purpose and scope

This document describes MEGO's server side. MEGO has no custom server of its own; the backend consists of (a) a Google Apps Script web app, apps-script/Code.gs (script version 5, Hub schema version 3), owned and run by the project owner, and (b) Firebase Authentication and Cloud Firestore as a managed backend whose behaviour is defined by security rules. The document covers the Apps Script request dispatcher, authentication, installation, the Hub tab model, write/conflict/delete rules, the Gemini proxy (owner path and public path) and the role of Firebase. Request/response field lists for every action are in MEGO_API_Documentation.

Access is "anyone" because a PWA cannot send Google login cookies; every request is therefore authenticated inside the script (section 4). The script is a standalone project. doGet() returns only {ok: true, app: "mego-nutrition", version: 5}. The client sends POST requests with Content-Type: text/plain to avoid a CORS preflight; responses are JSON produced by ContentService.

3. Request dispatcher (doPost)

doPost(e)
  req = JSON.parse(body)
  action == "bootstrap"                      -> bootstrap_(req)            (one-time secret)
  req.idToken and action in {analyzeMeal, aiStats} -> publicAi_(req)      (Firebase user)
  req.token != APP_TOKEN                     -> {ok:false, error:"unauthorized"}

  ScriptLock.waitLock(25 s):
     ping | foods | push | pull | saveFoods | backup | meta

  any exception                              -> {ok:false, error: message}

4. Authentication

  • App token (owner devices). setup() creates APP_TOKEN = two UUIDs without hyphens (64 hex characters) in Script Properties, if none exists. It is compared with req.token on every request. rotateToken() deletes and recreates it (all connected devices must then be reconnected). The token is never in the repository.
  • Firebase ID token (public accounts). Only for analyzeMeal and aiStats. verifyFirebaseUser_() calls Google Identity Toolkit accounts:lookup with the stored FIREBASE_API_KEY; a non-200 answer, missing user or disabled user returns unauthorized. The script then reads profiles/{uid} (and for aiStats admins/{uid}) through the Firestore REST API with the user's own token, so Firestore rules apply exactly as in the app.
  • Bootstrap secret. BOOTSTRAP_HASH is empty in the public repository (bootstrap disabled). The laptop setup writes the SHA-256 of a random secret only into the owner's private copy; the secret works once.

5. Installation: setup, installMego, bootstrap

installMego()                                   (run from the editor, or via bootstrap)
 1. setup()                -> APP_TOKEN (kept if it already exists)
 2. ensureNativeHub_()     -> convert the Excel Hub (SOURCE_ID) once into a native Google Sheet in the same
                              folder (Drive.Files.create); stored as HUB_PENDING_ID; the .xlsx is not modified
 3. verifyNativeHub_(id)   -> original food tab present, food rows counted, numeric problems counted;
                              fails with VERIFY_FAILED -> the Hub is NOT switched
 4. HUB_NATIVE_ID = id     -> switch only after successful verification; HUB_VERIFIED stored
 5. migrateHub()           -> Drive backup copy, rename to "MEGO Nutrition Hub", create structured and
                              derived tabs, seed Food_Database with stable ids F0001..., Hub_Dashboard,
                              Migration_Report (re-runnable, nothing duplicated)
 6. print the connection code "MEGO1|<web app URL>|<token>" (only once the web app is deployed)

Modes: native (the Hub is a native Google Sheet: full two-way sync) and xlsx (not converted yet: read-only; foods reads a temporary converted copy that is trashed immediately, pull returns empty tables with readOnly: true, writes fail with HUB_IS_XLSX). The script never opens any spreadsheet other than the Hub.

7. Write rules: validation, conflicts, soft delete

7.1 Validation (validChange_)

  • At most 500 changes per request; any invalid change rejects the whole request ("N invalid change(s) rejected").
  • Table must be in the whitelist; key a non-empty string ≤ 200 characters; op upsert or delete.
  • Upsert payload must be an object ≤ 45,000 JSON characters; diary entries need a YYYY-MM-DD date and numeric macros.kcal; body weight, if present, must be 20–400.

7.2 Conflict rule

For an upsert, the incoming timestamp is payload.updatedAt → payload.at → change.at. If the stored updated_at is greater, the change is not applied and {table, key} is returned in conflicts (an older copy never overwrites a newer one). Equal timestamps are applied.

7.3 Soft delete

A delete copies the row's json into Deleted_Records (table, key, deleted_at, json, recovered="no") before deleting the row. Deleting a key that does not exist is a no-op.

7.4 Versioning and metadata

If at least one change was applied, dataVersion is incremented and lastWriteAt (and appSchemaVersion when the client sends it) are written. lastSyncAt and lastConflicts are written on every push. The response is {ok, applied, conflicts, dataVersion}. All Hub-touching actions run inside a script lock (wait up to 25 s).

7.5 Food write-back and backups

saveFoods validates names and the four macro values (0–1000), makes a Drive copy of the Hub at most once per day (LAST_HUB_BACKUP), then reuses the push logic. migrateHub always makes a Drive copy first. Every backup is logged in Backup_Log.

8. Gemini proxy

8.1 Owner path (app token)

analyzeMeal_ runs outside the lock. It requires GEMINI_API_KEY, a base64 image ≤ 2,800,000 characters (JPEG, PNG or WebP), up to 800 food lines, and a note ≤ 300 characters. It enforces the global daily cap (AI_DAILY_LIMIT, default 40; counter AI_USED_<date>, incremented once the Gemini call is made), calls models/<model>:generateContent with a JSON response schema, temperature 0.2 and max 8,192 output tokens, and returns {ok, model, result}. Allowed models: gemini-3.8-flash (default), gemini-3.6-flash, gemini-3.5-flash-lite (property AI_MODEL). Nothing is stored.

8.2 Public path (Firebase ID token)

publicAi_(req)
  verifyFirebaseUser_(idToken)            -> uid, or unauthorized / CLOUD_NOT_CONFIGURED
  action aiStats -> admins/{uid} readable with the user's token? -> 7-day counts, else unauthorized
  profiles/{uid} (user's token): status must be "active"         -> else unauthorized
  country in EU/EEA/UK/CH list                                   -> AI_REGION_RESTRICTED
  lock 10 s; counter AI_U_<date>_<uid> >= AI_USER_DAILY_LIMIT (default 10) -> AI_USER_LIMIT
  counter + 1; analyzeMeal_(req)          (global cap and Gemini call shared with the owner path)

8.3 Error codes

AI_NOT_CONFIGURED, AI_BAD_IMAGE, AI_DAILY_LIMIT, AI_USER_LIMIT, AI_REGION_RESTRICTED, AI_QUOTA_DAY, AI_QUOTA_MINUTE (with retryAfter), AI_REGION, AI_KEY_INVALID, AI_MODEL_UNAVAILABLE, AI_BUSY (HTTP ≥ 500), AI_HTTP_<code>, AI_NETWORK, AI_REFUSED, AI_TRUNCATED, AI_BAD_OUTPUT. There is no retry on another model or service.

8.4 Key management

setAiKey accepts keys matching [A-Za-z0-9_.-]{20,200} (classic and newer key formats), checks them with a GET on the model metadata endpoint, and stores them only if Google answers 200. remove: true deletes the key. setCloudConfig stores FIREBASE_API_KEY and FIREBASE_PROJECT_ID (public identifiers) and optionally clamps AI_USER_DAILY_LIMIT to 1–50 and AI_DAILY_LIMIT to 1–1500. cleanupAiCounters() deletes counters older than 8 days.

9. Firebase as managed backend

For public accounts there is no server code: the client uses the Firebase SDK directly, and firebase/firestore.rules is the server-side policy. Key rules: a user reads/writes only users/{own uid}/** and only while the profile status is active; updates may not lower updatedAt; record shape and table names are validated; admins (presence of admins/{uid}, writable by nobody from the client) may list profiles and change only status, and have no access to users/**; shared foods are readable by active users and writable by admins; foodSubmissions and errorReports have their own limited rules. Details: MEGO_Firebase_Integration.
