Purpose and scope

This document describes how MEGO detects, presents, retries and records errors: UI crash protection, user-facing messages, validation errors, sync errors (Hub and Firestore), AI meal-scanner error codes on the backend and client, authentication errors, the reportError mechanism and the other logs that exist (Hub tabs, Apps Script logging). MEGO has no third-party error-tracking or analytics service; the only remote error log is the Firestore collection errorReports.

1. Principles

  • An error must never destroy or silently overwrite data: older copies are refused, deletes are soft on the Hub, local backups are taken before risky operations.
  • Temporary failures are retried automatically with backoff; permanent ones (bad token, wrong spreadsheet, quota, invalid key) are not retried and are shown to the user.
  • Reporting must never break the app (reportError swallows its own failures).
  • Error reports contain no personal data and never contain keys or tokens (the backend's google detail excludes the key).

2. UI crash protection (ErrorBoundary)

src/components/ErrorBoundary.tsx wraps the routed pages inside the layout and is keyed by the current path, so navigating to another page resets it. When a render error occurs it:

  • logs console.error('UI error', error) in the browser console;
  • shows a recovery card (data-testid="error-screen") with a translated title and body, the error message (LTR), and two buttons: Retry (clears the error and re-renders) and Reload (goes to #/ and reloads).

Data lives in IndexedDB and is not affected by a UI error. UI crashes are not sent to errorReports.

3. User-facing errors and validation

Most actions run through useAsync().run() (src/components/ui.tsx): it sets a busy flag, shows an optional success toast, and on failure shows a toast "Error: <message>" (a DUPLICATE: error is shown as the translated "duplicate food" message).

Thrown by (src/lib/repo.ts)Message
createFood / updateFoodInvalid nutrition values: …, Name is required, DUPLICATE:<food id>, Food not found
saveSettingsInvalid targets: kcal, protein … (kcal must be > 0, macros ≥ 0)

Destructive confirmations (e.g. Hub change HUB_CHANGED) use a confirmation dialog before anything is changed.

4. Boot-time errors

  • preMigrationBackup() and preUpdateBackup() failures are logged with console.warn and do not stop the app.
  • bootAccount() failure falls back to guest mode.
  • A missing firebase-config.json or any fetch/parse error → guest-only mode (no error shown).
  • A signed-in session that has expired or belongs to another uid → the active account is cleared and the page reloads to the welcome screen.

On failure: backoffMs(n) = min(300000, 5000 × 2^(n−1)), sync.lastError is stored in settings, and the status chip shows error (or offline) with "retry in N s". Hub sync errors are not sent to errorReports (guest/owner devices are usually not signed in).

6. Sync errors: Firestore

  • permission-denied on push: counted as a conflict (the server holds a newer copy, or the account is suspended); the item is removed from the outbox.
  • Other push errors: the run stops, status error with the message, reportError('sync', message).
  • Applying a received record fails: reportError('sync-apply', '<table>/<id>: <message>'); the download continues with the next record.
  • Listener error: status error with the message. The shared-foods listener ignores errors (offline: the local copy keeps working).
  • Offline: status offline; pushes resume 300 ms after the browser is online again.

Model chain (free tier only): gemini-3.8-flash → gemini-3.6-flash → gemini-3.5-flash-lite; overall deadline 240 s. Each failed attempt is logged with console.warn('Gemini <model> → <code> …') in Apps Script (exception logging: STACKDRIVER). Other backend codes: AI_NOT_CONFIGURED, AI_DAILY_LIMIT, AI_USER_LIMIT, AI_REGION_RESTRICTED, AI_REFUSED, AI_BAD_OUTPUT, AI_TRUNCATED. A failed analysis does not use up the daily allowance (global counter only on success; per-user counter refunded).

7.2 Client handling (src/lib/mealScanner.ts, MealScanner.tsx)

  • Image validation before sending: AI_UNSUPPORTED_FORMAT (not an image or cannot be decoded — the original is never sent), AI_IMAGE_TOO_LARGE (> 30 MB, or still over the upload limit after shrinking).
  • Before the request: AI_NO_BACKEND (no backend configured / not signed in), AI_OFFLINE; client timeout after 280 s → AI_TIMEOUT.
  • Mapping of backend answers: AI_QUOTA_DAY gets the reset time (midnight America/Los_Angeles, shown in local time); AI_QUOTA_MINUTE gets seconds; AI_USER_LIMIT gets the limit; AI_HTTP_* → AI_SERVER_ERROR; unauthorized → AI_UNAUTHORIZED; unknown action → AI_OLD_BACKEND; HTTP 5xx → AI_SERVER_ERROR; HTTP 4xx → AI_CONFIG; anything else → AI_NETWORK. Google's status/message is passed through as a detail line ("Google said: …").
  • Automatic retry: temporary codes (AI_OVERLOADED, AI_SERVER_ERROR, AI_TIMEOUT, AI_NETWORK, AI_BUSY) after 3 s and 8 s (not AI_NETWORK while offline); a per-minute quota of ≤ 20 s is waited out. The screen shows "retrying n/2 (reason)". The same image is never sent twice at once.
  • On final failure the translated message is shown (unknown codes → AI_ERROR); for temporary errors the photo is kept so the user can retry manually.
  • Results are validated (AI_BAD_OUTPUT if malformed); nothing is saved automatically.

Root cause of the former generic "AI is busy" message: Google 503 overload on the primary model, which the old backend reported as busy without retry (fixed in backend version 7).

8. Authentication errors

Firebase errors are mapped by code (auth/…) to translated messages with the prefix authErr_; unknown codes use authErr_generic. Mapped codes: email_already_in_use, invalid_credential, invalid_email, network_request_failed, requires_recent_login, too_many_requests, user_disabled, user_not_found, weak_password, wrong_password. Profile updates that fail while offline or suspended are ignored (touchProfile).

9. Error reporting: reportError and errorReports

reportError(kind, message)
  └─ only if Firebase is initialised AND a user is signed in
  └─ setDoc(errorReports/<auto id>, { at: Date.now(), kind: kind[0..40], message: message[0..400], app: '1' })
  └─ any failure is swallowed
Kind (current callers)When
syncA Firestore push run failed with an error other than permission-denied
sync-applyA received record could not be applied locally
  • Security rules: any signed-in user may create a report with only the keys at/kind/message/app and a message under 500 characters; only admins may read or delete.
  • Admin dashboard (#/admin): adminListErrors(50) lists the newest 50 reports (kind chip, message, date). No automatic alerting exists.
  • No retention or clean-up job exists for errorReports (Not verified whether reports are deleted manually).
