Purpose and scope

This document describes how MEGO uses Firebase (Firebase Authentication and Cloud Firestore on the free Spark plan) for public, multi-user accounts. It covers the client modules src/lib/firebase.ts, src/lib/account.ts and src/lib/cloudSync.ts, the server-side security rules in firebase/firestore.rules, and the recovery fix for the 10 Nov 2026 storage-loss incident (the mego.cloud2. markers). Setup steps are in MEGO_Firebase_Setup_Guide; the Google Sheets Hub sync used by guest/owner devices is described in MEGO_Google_Sheets_Integration_and_Sync.

1. Overview and operating modes

Firebase is optional at runtime. At boot, bootAccount() fetches firebase-config.json from the app's base path. If the file is absent or lacks apiKey/projectId, the app runs in guest mode (this device only) exactly as before accounts existed. If it is present, the app has three modes (AccountState.mode):

The SDK is the firebase npm package, version 13.1.0 (package.json).

2. Configuration loading and initialisation (firebase.ts)

2.1 CloudConfig

loadCloudConfig() reads BASE_URL + 'firebase-config.json' with cache: 'no-cache', once per session; any error returns null (guest mode).

2.2 initCloud()

  • Initialises the Firebase app with apiKey, authDomain, projectId and appId.
  • Production Firestore is created with initializeFirestore(..., { experimentalAutoDetectLongPolling: true, experimentalLongPollingOptions: { timeoutSeconds: 10 } }), because some networks buffer Firestore's streaming channel; auto-detection switches those clients to long polling.
  • With an emulator block, the app connects to the Auth and Firestore emulators (ports in firebase.json: auth 9099, firestore 8080).
  • cloud() throws CLOUD_NOT_CONFIGURED when called before initialisation.

4. Session and per-account local database (account.ts)

4.1 Boot sequence

  1. loadCloudConfig(); no config → guest mode.
  2. initCloud(cfg).
  3. If mego.activeUid is set: check with Dexie.exists('mego-u-<uid>') whether the local database still exists. If it is missing, resetCloudMarkers(uid) is called so the cloud listener downloads everything again (section 6).
  4. useDatabase('mego-u-<uid>') and open it; copy guest data once if mego.importGuestFor equals this uid; apply the pending registration answers (mego.pendingSetup.<uid>) once.
  5. Otherwise mode is guest (if mego.guest) or welcome.

4.2 watchSession()

In account mode, onAuthStateChanged confirms the Firebase session. If the user is signed out or the uid differs, mego.activeUid is removed and the page reloads. Otherwise the profile and admin flag are loaded, suspended is set when status === 'suspended', lastActiveAt is touched, and cloud sync is started once (never for a suspended account).

4.3 Switching accounts

  • enterAccount(uid, importGuest) sets mego.activeUid, clears mego.guest, optionally sets mego.importGuestFor, and reloads the page so the right database is selected before anything renders.
  • copyGuestData() copies every sync table from mego-nutrition into the account database (the guest database is left untouched; the account's device-local sync setting is kept), queues every copied record in the outbox for upload, and copies progress photos (local only).
  • chooseGuest(), leaveAccount() also reload.

5. Cloud sync (cloudSync.ts)

5.1 Push

  • Uses the same Dexie outbox as the Sheets sync. Queued changes are coalesced (latest change per table+key).
  • Each record is written with setDoc to users/{uid}/{table}/{key} as { data: JSON string, updatedAt, deleted? }. A delete is { data: '{}', updatedAt, deleted: true } (a tombstone, not a document deletion). For settings, the device-local sync block is removed before upload.
  • Shared verified foods (source: 'sheet') are never pushed; personal foods are.
  • A permission-denied answer is counted as a conflict (the server already has a newer copy, or the account is suspended); the record is removed from the outbox and the newer copy arrives through the listener. Any other error stops the run, sets status error and calls reportError('sync', …).
  • Scheduling: 1.5 s after a local change, 300 ms after the browser goes online, 500 ms after start. When the browser reports offline, the status becomes offline and nothing is sent.

5.2 Pull (live listeners)

  • One onSnapshot listener per sync table: where('updatedAt', '>', from), where from comes from startFrom() (section 6).
  • applyRemote() keeps the newer copy: if the local record's updatedAt (or at) is newer, the remote copy is ignored (the local one will be pushed). Tombstones delete the local record.
  • Each applied record advances the "last seen" marker for that table (setLast, only upwards).
  • A record that cannot be applied is reported with reportError('sync-apply', '<table>/<id>: …') and does not stop the rest of the download.
  • An additional listener on /foods imports the shared verified food database into the local food list as source sheet; when offline the local copy keeps working.

6. Recovery fix: cloud2 markers and storage loss

Incident (10 Nov 2026): on an Android phone, the browser lost the IndexedDB data (records and the Firebase session) while localStorage survived. The app showed the welcome screen; after signing in again the account stayed empty, because the listener started from "last seen" markers still present in localStorage, and a freshly created default settings record outranked the saved settings. It had happened once before. The fix is live; it was reproduced and verified on emulators (e2e/storage-loss.mjs), and the owner confirmed the data came back.

FixWhereEffect
Markers renamed to mego.cloud2.<uid>.<table>cloudSync.ts (MARK)Markers of the first version are ignored once, so every device re-downloads its account in full one time; newer local copies are kept.
Missing local database resets markersaccount.ts → resetCloudMarkers(uid)If mego-u-<uid> no longer exists, all markers of that account are removed (non-destructive).
Empty table downloads in fullcloudSync.ts startFrom()If a local table has 0 records, the listener starts from 0 regardless of the marker.
Settings always re-readstartFrom()settings (one document) always starts from 0.
Untouched defaults never outrank cloud copiesrepo.ts getSettings() creates defaults with updatedAt: 0; cloudSync.ts isPristineDefault()A local settings record equal to the defaults (ignoring id, timestamps and sync) is always replaced by the account's settings.
One bad record never stops the downloadlistener try/catchError reported as sync-apply; others continue.
Same-date weigh-ins keep the newer oneapplyRemote() for bodyThe local unique index allows one measurement per date; if another id exists for the same date, the newer one is shown on the device; the other stays untouched in the cloud.

Lesson for users: signed-in accounts are recoverable by signing in again; guest data lives only on the device.

8. Security rules (firestore.rules)

Helper functions: signedIn(), isAdmin() (an admins/{uid} document exists), isActive() (own profile exists and status == 'active'), isOwner(uid).

Valid record: keys only data/updatedAt/deleted, updatedAt is int, data is a string under 300,000 chars, deleted is bool if present, table in the allowed list.
profiles/{uid}owner or admincreate: owner, fixed key set, status 'active', ageConfirmed true, email equals the token's e-mail; update: owner while active (only displayName, country, lastActiveAt) or admin (only status, to 'active'/'suspended'); delete: owner

Because rules are enforced by Google's servers, a suspended account loses read and write access to its private records immediately, even if the client keeps running.

9. Admin functions and shared foods

  • adminStats(): aggregate counts via getCountFromServer — total profiles, active in the last 7 days, suspended, pending food submissions.
  • adminListProfiles(max = 100), adminSetStatus(uid, status), adminListErrors(max = 50) (newest first).
  • submitFood(): a user proposes one of their foods (never published automatically). adminReview(): approve copies the food into foods/U-<submission id> with a note "user submission reviewed by admin"; both approve and reject set the submission status.
  • publishSharedFoods(foods) (cloudSync.ts, admin screen): writes verified foods to /foods, using the sheet key (F0001-style) when present; refused by the server for non-admins.

Admins never see private diary, weight or settings records (rules, section 8). Administration procedures are in MEGO_Admin_User_Manual.
