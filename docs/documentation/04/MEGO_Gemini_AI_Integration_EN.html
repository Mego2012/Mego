Purpose and scope

This document describes how the MEGO AI Meal Scanner uses the Google Gemini API (free tier only): which code is involved, what data leaves the phone, how the request and response are structured, how the result is matched to the food database and reviewed by the user, and which errors and limits exist. Sources: src/lib/mealScanner.ts, src/components/MealScanner.tsx, the "AI meal scanner" and "public accounts — AI proxy" sections of apps-script/Code.gs, and the AI error texts in src/lib/i18n2.ts.

1. Design principles

  • Free tier only, no paid fallback. The backend only allows the models in AI_FREE_MODELS = gemini-3.8-flash (default, AI_DEFAULT_MODEL), gemini-3.6-flash, gemini-3.5-flash-lite. The optional Script Property AI_MODEL is ignored unless it is one of these. There is no fallback model and no other AI service; a quota error is shown to the user, nothing is retried elsewhere.
  • The key never reaches the phone. The Gemini key is stored only in the Apps Script Script Property GEMINI_API_KEY. The app sends it once through the setAiKey action and does not keep it.
  • The AI identifies, the app calculates. The model only identifies foods, estimates grams, state and cooking method and picks the matching database row. All nutrition values are computed in the app with the same engine as manual logging (macrosFor on the food's per-100 g basis).
  • Nothing is saved automatically. The meal is written to the diary only when the user presses "Confirm and save".

3. Image preparation (resize and EXIF removal)

  1. prepareImage(file, max = 1024) rejects non-image files (AI_BAD_IMAGE).
  2. The photo is drawn on a canvas via compressImage (src/lib/repo.ts): longest side scaled to at most 1024 px, re-encoded as JPEG at quality 0.82. Re-encoding through a canvas drops all metadata (EXIF: GPS location, device, time) — only pixels are sent.
  3. If the browser cannot decode/re-encode the image, the original file is never sent (AI_BAD_IMAGE).
  4. If the result is larger than 1,500,000 bytes it is re-encoded at 768 px.
  5. The JPEG is converted to base64. The backend rejects images larger than AI_MAX_IMAGE_CHARS = 2,800,000 base64 characters (≈ 2 MB) or containing non-base64 characters.

4. Request to the backend and to Gemini

4.1 What the app sends

FieldContent
actionanalyzeMeal
imagebase64 JPEG (EXIF removed)
mediaTypeimage/jpeg (backend accepts jpeg/png/webp, anything else becomes jpeg)
foodscatalog lines {k, ar, en, s, c}: short key (f1, f2…), Arabic name, English name, state, category — only non-archived, complete foods. No diary, weight or profile data.

noteoptional user note, max 300 characters
token or idTokenowner APP token (private backend) or Firebase ID token (public accounts)

Privacy note from Code.gs: on the free tier Google may use requests to improve its products and human reviewers may see them; therefore the request contains only the meal photo and food names. Nothing about the meal is stored by the backend.

4.2 Gemini call (backend)

  • Endpoint: https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent, key in the x-goog-api-key header.
  • systemInstruction: the fixed prompt AI_SYSTEM (identify every visible food incl. oil/sauces, estimate edible grams as shown with a low–high range, raw/cooked/other, cooking method, match to the database in the same state or leave food_key empty, confidence below 0.6 for uncertain items, no people/places in the output).
  • contents: the image as inlineData plus a text part with the user language, optional note and the database lines key | Arabic | English | state | category (max AI_MAX_FOODS = 800 rows, each field max 120 chars, | and newlines removed).
  • generationConfig: responseMimeType: application/json, responseJsonSchema: AI_SCHEMA, maxOutputTokens: 8192, temperature: 0.2, thinkingConfig.thinkingLevel: MEDIUM.
  • The call runs outside the script lock because it can take ~10–40 s. The app times out after 120 s (AI_TIMEOUT).

Backend handling: promptFeedback.blockReason or a finish reason other than STOP → AI_REFUSED; MAX_TOKENS → AI_TRUNCATED; no candidate or invalid JSON → AI_BAD_OUTPUT; "thought" parts are ignored. On success: {ok:true, model, result}.

App re-validation (validateAiResult): strings cut to 300 chars, at most 30 items, unknown enum values replaced (state → other, method → unknown, kind → food), grams rounded and clamped to 0–3000 (MAX_GRAMS), confidence clamped to 0–1, items without a name or with 0 g dropped.

6. Matching to the food database and estimates

toScanItems converts each AI item into an editable ScanItem and sets flags:

FlagConditionEffect
badKeyfood_key not in the catalogtreated as not in the database
stateMismatchdatabase food raw and AI says cooked (or vice versa)match removed — the app never converts raw ↔ cooked
notInDbno valid matchAI estimate used only if it passes validateMacros and kcal > 0
lowConfidenceconfidence < 0.6 (LOW_CONFIDENCE)user must tick "I checked this item"
hiddenFatkind oil_or_fat or sauce_or_dressinguser must tick "I checked this item"

Nutrition per item (itemNutrition): database food → macrosFor(basisFromFood(food), grams, 'g') (labelled "from database"); otherwise the AI per-100 g estimate scaled by grams/100 (labelled "estimate", shown with "~"). Meal totals show a warning when estimates are included. For unmatched items suggestFoods proposes up to 3 database foods with matching name words (same state scores higher); suggestions are only applied when the user taps them.

7. Review and save flow

  1. The user takes a photo or picks one from the gallery (ScanButtons), optionally writes a note and taps Analyse. Stages: ready → preparing → analyzing → review (or error). Analysis can be cancelled.
  2. In review the user can change grams, cooking method, state (unmatched items), choose/change the database food, remove items, add ingredients via the food picker, and change meal (suggested from the time of day) and date.
  3. The save button stays disabled while blockers() returns reasons: empty, grams (≤ 0 or > 3000), unmatched (no food and not "add as new"), unconfirmed.
  4. logScannedMeal: unmatched items the user chose to add become new foods with category «تقدير من صورة» and the note "AI photo estimate — unverified, please review"; grams of the same food are merged into one entry; saving is all-or-nothing (entries already added are deleted on failure).
  5. A toast offers Undo: it deletes the entries and archives the foods created by the scan.

The global counter is incremented after each Gemini call attempt that reached Google; the per-user counter before the call. The optional function cleanupAiCounters() (manual or time trigger) deletes counters older than 8 days. Account requests also require the profile status to be active.

10. Verification status

  • Verified live (7 Nov 2026): Gemini key stored only in Script Properties; one real photo analysis with gemini-3.8-flash succeeded (6 items, ~72 s); a later run returned AI_BUSY (transient Google overload). Key formats AIza… and AQ.… are accepted; Google validates the key with a model metadata call.
  • Tested with automated tests only: scanner logic and backend paths in tests/scanner.test.ts (part of the 109 unit tests), e.g. the admin-only aiStats.
  • Not verified: real scans by public (Firebase) accounts in production; the region restriction against real accounts; quota reset timing against Google; scanning on a real Android device.
