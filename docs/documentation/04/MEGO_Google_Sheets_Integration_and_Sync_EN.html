Purpose and scope

This document explains how the MEGO app synchronises a guest/owner device with the MEGO Nutrition Hub, a Google Sheet served by a private Google Apps Script web app. It covers the client src/lib/sync.ts (plus the Settings screen that drives it) and the server apps-script/Code.gs. Signed-in public accounts do not use this path; they sync through Firestore (MEGO_Firebase_Integration). The individual request/response formats are listed in MEGO_API_Documentation.

Principles (from the Code.gs header and sync.ts): one source of truth (the Hub only); every write is timestamp-checked so an older record never overwrites a newer one; deletes are soft (copied to Deleted_Records); the original Excel file and the original food tab are never modified.

2. The Hub and its identity checks

  • The Hub started as an Excel file. installMego() converts it once into a native Google Sheet in the same folder (a new file ID); the Excel file is kept untouched as the backup. Backend mode is native (two-way) or xlsx (read-only; writes fail with HUB_IS_XLSX).
  • The client constant HUB_ID (sync.ts) and the server constant SOURCE_ID (Code.gs) hold the same original file ID. File IDs are not reproduced here.
  • checkHub() on every connection: the backend's reported sourceId must equal HUB_ID, otherwise WRONG_SPREADSHEET. The native ID is pinned on the phone (settings.sync.hubNativeId) at the first successful connection; a later different native ID raises HUB_CHANGED, which the Settings screen only accepts after a confirmation dialog.
  • assertHub() runs this check once per session before any data exchange.

3. Connecting a device

3.1 Connection code

The setup prints a one-line code of the form MEGO1|<web app URL>|<token>. parseConnectionCode() accepts it only if the URL starts with https://script.google.com/ and the token is 32–128 letters/digits. The laptop setup can also show a QR code / link that opens #/settings?connect=…; the Settings screen connects once and removes the parameter from the address bar. The code contains a secret and must never be shared.

3.2 Connect flow (Settings → Sync)

  1. Save URL, token, auto-sync and write-back options in settings.sync (device-local; never uploaded).
  2. testConnection() → action ping; Hub identity check and pinning; the app shows the sheet name, food tab, writable / read-only, and AI scanner on/off.
  3. If the Hub is read-only, stop here.
  4. checkHubFoods() compares the Hub's foods with the shared foods on the phone (read-only). If any values differ, the flow stops and the differences are shown — nothing is overwritten silently.
  5. Otherwise: local backup pre-import, pullFoodsFromSheet(), queueFullUpload(), pushNow().

5. Push (phone → Hub)

5.1 Client (pushNow)

  1. Skip with status disabled if URL or token is empty; offline if the browser is offline.
  2. Hub identity check (assertHub).
  3. Loop: read up to 300 outbox items (by id), coalesce to the latest change per table+key.
  4. Shared foods (source: 'sheet') are removed from the batch — food values belong to the Hub. If write-back is enabled (writeFoodsToSheet), edited shared foods are sent separately with action saveFoods.
  5. Send action push with changes and clientSchema (Dexie schema version 2). On success the batch is removed from the outbox; dataVersion is stored in sync.serverVersion.
  6. If the answer lists conflicts (the Hub holds newer versions), the conflict counter increases and pullAll() brings those records back instead of overwriting.
  7. On success: sync.lastPushAt set, sync.lastError cleared, status idle.

5.2 Server (push_)

  • Runs inside a script lock (waitLock(25000)) and only in native mode.
  • Limits: at most 500 changes per request (MAX_CHANGES); key up to 200 characters; payload JSON up to 45,000 characters. The whole request is rejected if any change is invalid ("<n> invalid change(s) rejected").
  • Validation: table must be known; op upsert or delete; for entries the date must be YYYY-MM-DD and macros.kcal a number; for body a weight, if present, must be a number from 20 to 400.
  • Conflict rule: if the stored updated_at is greater than the incoming updatedAt (or at), the change is skipped and reported in conflicts.
  • Delete: the row's JSON is copied to Deleted_Records (table, key, deleted_at, json, recovered = "no"), then the row is removed.
  • Metadata: when something was applied, dataVersion increments and lastWriteAt / appSchemaVersion are written; lastSyncAt and lastConflicts are written on every push.

6. Pull (Hub → phone)

  • pullAll() (Settings button "Restore from sheet", after a local backup pre-pull) calls action pull, which returns the json column of every structured tab (in xlsx mode an empty result marked readOnly).
  • Foods are skipped here (they come through the food import with stable IDs).
  • Merge rule: a row is written locally only if no local record exists or the remote updatedAt/at is newer. For settings, the remote copy wins only if newer, and the device-local sync block is always kept.
  • Nothing local is deleted by a pull. sync.lastPullAt is updated. The server also supports since (incremental), but the client does not send it.

7. Foods: import, comparison and write-back

  • pullFoodsFromSheet(): action foods returns rows from Food_Database (structured) or, if absent, from the original Arabic food tab; parsed with parseStructuredFoods or parseFoodRows and merged with importParsedFoods(…, 'sheet') (never deletes local records).
  • checkHubFoods(): read-only comparison by Arabic name + state → identical, different (kcal, protein, carbs, fat, piece grams), only in Hub, only on phone.
  • saveFoods (server): up to 200 foods; each needs a name and kcal/protein/carbs/fat numbers from 0 to 1000; a full Drive copy of the Hub is made once per day before the first write-back; values are written to Food_Database only, never the original tab.
  • fillFoodNames (server, since backend SCRIPT_VERSION 8): takes an Arabic → English name map and writes only empty name_en cells of Food_Database (non-empty names and all other cells stay unchanged), after the daily Drive backup. It is called by the laptop command, not by the app.
  • node scripts/laptop-setup.mjs --hub-complete-foods: updates the backend, then adds to the Hub's Food_Database every recipe-library ingredient that is missing (USDA values) and every library meal as a ready food (id LIB-<recipe id>, values computed from the Hub's own values, per 100 g of raw ingredients, 1 serving as the piece weight) through saveFoods in batches of 100, then fills empty English names through fillFoodNames. Existing rows and values are never changed; ingredients without verified values are listed and never estimated; meals with such an ingredient are skipped.

8. Scheduling, status and retries

Trigger (startAutoSync)Delay
App start1 s
Local change (onLocalChange)2.5 s (debounced)
Browser back online / app visible again0.5 s
Periodicevery 60 s

Each trigger pushes only when settings.sync.autoSync is on (default on); otherwise it just refreshes the pending count. The header sync chip shows disabled, offline, idle, syncing or error, plus the number of pending changes and, after an error, "retry in N s". Tapping it pushes immediately (or opens Settings when disabled).

Backoff after failures: backoffMs(n) = min(300000, 5000 × 2^(n−1)) → 5 s, 10 s, 20 s … capped at 5 min. Errors matching unauthorized, WRONG_SPREADSHEET or HUB_IS_XLSX are permanent and are not retried automatically. The last error is stored in sync.lastError.

9. Backups related to sync

  • Local backups before risky steps: pre-import (connect flow), pre-pull (restore from sheet).
  • Server: migrateHub() makes a Drive copy first ("BACKUP MEGO Nutrition Hub — before migrateHub — …"); daily copy before the first food write-back; action backup stores an app snapshot JSON in the Drive folder "MEGO Nutrition Backups" and logs it in Backup_Log.

Full procedures: MEGO_Data_Backup_and_Recovery.
