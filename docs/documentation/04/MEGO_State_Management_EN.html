Purpose and scope

This document explains where MEGO keeps its state and how changes flow through the app: the React context (src/app/AppContext.tsx), the data hooks (src/app/hooks.ts), Dexie live queries over IndexedDB, the repository layer and its change notifications (src/lib/repo.ts), the generic key/value table (kv) and its keys, and the small module-level stores for account and sync status. MEGO uses no external state library (no Redux, Zustand or similar); the local database is the single source of truth.

1. Design principles

  • Database first: persistent data lives in IndexedDB (Dexie). Screens read it through live queries, so any write — local, from the Hub pull or from the Firestore listener — re-renders the affected screens automatically.
  • One write path: every persistent change goes through repo.ts (or modules built on it), which also queues the change in the outbox for sync.
  • Settings are data: the settings record (settings/main) is read through a live query in AppContext, so language, theme and targets change everywhere at once.
  • Component state is local: forms, dialogs and selections use React useState inside the component.

3. AppContext

AppProvider wraps the whole app (outside the router). It reads db.settings.get('main') with useLiveQuery and merges it over defaultSettings() (nested merge of profile, targets, tolerance and sync), so new setting fields always have a value.

5. Writes: repository, outbox and change notifications

  1. A screen calls a repository function (e.g. addFoodEntry, saveSettings, kvSet).
  2. The function validates (e.g. validateMacros, validateTargets, duplicate check), writes the Dexie table (in a transaction where several tables change) and calls enqueue(table, key, op, payload).
  3. enqueue adds an outbox item { table, key, op, payload, at } and notifies every onLocalChange listener.
  4. Listeners: the Hub auto-sync (startAutoSync, push after 2.5 s) or the Firestore sync (startCloudSync, push after 1.5 s), depending on mode.
  5. Dexie live queries re-render the screens that read the changed tables.

Settings specifics: getSettings() creates the default record with updatedAt: 0 on first run, so an untouched default never outranks the account's settings arriving from the cloud. saveSettings(update) clones the current settings, applies the update, validates training and rest targets (kcal > 0, macros ≥ 0), sets updatedAt, writes, and queues the record without the sync block.

Incoming changes: the Firestore listener (applyRemote) and the Hub pull (pullAll) write Dexie directly (not through the outbox) and keep the newer copy by updatedAt; the live queries then update the UI.

6. The kv table and its keys

kv (Dexie v2, primary key key, index updatedAt) stores records { key, value, updatedAt }. It is synced like the other tables (Firestore users/{uid}/kv/{key}; Hub tab App_KeyValue). Helpers in repo.ts: kvGet(key, fallback), kvSet(key, value), kvDelete(key). New features since the 7 Nov release store their data here, so the Dexie schema is still version 2.

7. Module-level stores: account and sync status

  • account.ts keeps AccountState { mode, cloud, uid?, profile?, admin?, suspended? } with accountState(), subscribeAccount(fn) and an internal set() that notifies listeners. React reads it through useAccount() (src/pages/accountHook.ts, kept separate so the main bundle does not load the Firebase screens). Routed in App.tsx uses it to show the welcome, suspended or legal pages without the app shell.
  • sync.ts keeps SyncStatus { state, pending, lastPushAt?, error?, retryIn?, conflicts? } with subscribeSync and setStatus. Both the Hub sync and the Firestore sync report into it; the header chip reads it with useSyncStatus() (Layout.tsx).
  • Switching account or guest mode always reloads the page, so no in-memory state from the previous account survives.

8. Boot order and database selection

  1. preMigrationBackup() — snapshot before a Dexie upgrade (if needed).
  2. bootAccount() — selects mego-nutrition or mego-u-<uid> (useDatabase) before anything renders.
  3. preUpdateBackup() — once per release (APP_RELEASE).
  4. getSettings() — creates defaults on first run.
  5. React renders <App/> inside StrictMode.
  6. Account mode: watchSession → startCloudSync; otherwise startAutoSync (Hub). Then reminders, daily local backup, service-worker registration.
