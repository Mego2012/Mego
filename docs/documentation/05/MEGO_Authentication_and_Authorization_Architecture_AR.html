الغرض والنطاق

تشرح هذه الوثيقة البنية التي تحدّد هوية الطرف المتصل (المصادقة Authentication) وما يُسمح له بفعله (التفويض Authorization) في MEGO. وهي تسمّي كل آلية هوية وكل نقطة إنفاذ وكل دور، وتوضّح أين يُتخذ كل قرار فعليًا. أما سلوك الجلسة خطوة بخطوة (شاشات التسجيل، وتسجيل الخروج، وإعادة تعيين كلمة المرور) فموثّق في MEGO_Authentication_and_Session_Management، وقواعد Firestore سطرًا بسطر في MEGO_Access_Control_and_Permissions. لا تتضمن الوثيقة أي قيمة سرية؛ تُذكر الأسرار بأسمائها فقط.

1. نظرة عامة على البنية

MEGO تطبيق ويب تقدّمي (PWA) ثابت يُستضاف على GitHub Pages، وليس له خادم تطبيق خاص به. لذلك تعتمد المصادقة والتفويض على خدمتين من Google تفرضان القواعد على خوادمهما، إضافةً إلى تطبيق ويب على Apps Script يشغّله المالك.

 Phone / browser (PWA, untrusted client)
   │
   ├── Firebase Authentication (Email/Password) ──► issues a short-lived ID token
   │         │
   │         ▼
   ├── Cloud Firestore ──► firebase/firestore.rules evaluated by Google on every request
   │                        (identity = request.auth.uid, role data = profiles/, admins/)
   │
   └── Apps Script web app (apps-script/Code.gs, runs as the owner)
             ├─ owner/guest device: shared secret APP_TOKEN (Script Properties)
             ├─ signed-in user (AI scanner only): Firebase ID token → verified with Google
             │     Identity Toolkit, then profile read WITH THE USER'S TOKEN (rules apply)
             └─ one-time install: bootstrap secret checked against a SHA-256 hash

المبدأ: لا يُوثق بالمتصفح أبدًا. إخفاء الأزرار في الواجهة (مثل لوحة المشرف) وسيلة راحة فقط؛ أما القرار الحقيقي فتتخذه قواعد Firestore أو معالج doPost في Apps Script.

2. آليات الهوية

الآليةمن يستخدمهاكيف يُتحقق منهاالشيفرة
مصادقة Firebase بالبريد وكلمة المرور (Email/Password) على الخطة المجانية Sparkكل حساب عامتصدر Google رمز هوية (ID token) بعد التحقق من كلمة المرور، ويصل إلى Firestore بوصفه request.authsrc/lib/firebase.ts (register، login، logout، resetPassword)

سر التهيئة لمرة واحدة (bootstrap)سكربت إعداد الحاسوب، مرة واحدةيجب أن تطابق بصمة SHA-256 للسر قيمة BOOTSTRAP_HASH، ثم يتعطل عبر BOOTSTRAP_DONE. القيمة فارغة في المستودع العام = معطَّلbootstrap_ في Code.gs؛ scripts/laptop-setup.mjs
حساب Google الخاص بالمالك (OAuth)المالك فقط أثناء الإعدادتسجيل دخول Google؛ يُستخدم لنشر القواعد وكتابة admins/{uid}scripts/laptop-setup.mjs
بلا هوية (وضع الضيف)أي شخص يستخدم التطبيق دون حسابلا ينطبق — لا تغادر البيانات الجهاز ما لم يضبط المالك اتصالًا بالـ Hubsrc/lib/account.ts

إعدادات الويب الخاصة بـ Firebase ‏(public/firebase-config.json) معرّف عام للمشروع وليست بيانات اعتماد. إذا غاب الملف يعمل التطبيق في وضع الضيف فقط.

الأدوار مستقلة: المشرف مستخدم عادي فيما يخص بياناته الخاصة، ودور المشرف لا يمنح أي وصول إلى السجلات الخاصة لأي شخص.

4. نقاط الإنفاذ

#نقطة الإنفاذما تقرّرهموثوقة؟
4.1مصادقة Firebaseالتحقق من كلمة المرور، وتفرّد الحساب، وإصدار الرموز، والحد من محاولات الدخول (too-many-requests)نعم (Google)
4.2قواعد أمان Firestore ‏(firebase/firestore.rules)كل قراءة/كتابة للملفات الشخصية والسجلات الخاصة والأطعمة المشتركة والمقترحات وتقارير الأخطاءنعم (Google)
4.3doPost في Apps Scriptفحص الرمز لإجراءات الـ Hub؛ وفحص رمز الهوية والحساب النشط والدولة والحدود اليومية لوسيط الذكاء الاصطناعي؛ وفحص المشرف لـ aiStatsنعم (يعمل داخل حساب Google الخاص بالمالك)
4.4العميل (account.ts، Account.tsx)أي شاشة تظهر (ترحيب، إيقاف، مشرف)، وأي قاعدة بيانات محلية تُفتحلا — للراحة فقط

يقرأ وسيط الذكاء الاصطناعي في Apps Script المستندين profiles/{uid} وadmins/{uid} عبر واجهة Firestore REST برمز المستخدم نفسه، فتنطبق عليه قواعد Firestore ذاتها التي تنطبق على التطبيق؛ ولا يملك الوسيط أي صلاحية مطلقة على Firestore.

5. مسارات التفويض

5.1 مستخدم مسجّل يقرأ بياناته أو يكتبها

  1. يكتب التطبيق users/{uid}/{table}/{key} عبر مكتبة Firebase، ويُرفق رمز الهوية تلقائيًا.
  2. يتحقق Firestore من: request.auth.uid == uid، ووجود ملف شخصي حالته active، وصحة شكل السجل، وأن updatedAt لا يرجع إلى الوراء عند التحديث.
  3. أي إخفاق يعيد permission-denied، وتعامله شيفرة المزامنة كتعارض (الخادم يحمل نسخة أحدث، أو الحساب موقوف).

5.2 إجراءات المشرف

  1. عند بدء التشغيل تستدعي watchSession() الدالة isAdmin(uid): تكون صحيحة إذا أمكن قراءة admins/{uid} (ولا يقرؤه إلا صاحبه).
  2. تستدعي اللوحة adminStats (أعداد فقط) وadminListProfiles وadminSetStatus وadminListErrors وadminListSubmissions وadminReview وpublishSharedFoods. تُفحص كل عملية مجددًا بالقواعد (isAdmin())، ومن يفتح الشاشة قسرًا دون صلاحية يتلقى 403.

5.3 ماسح الوجبات بالذكاء الاصطناعي لمستخدم مسجّل

app ──(idToken, image)──► doPost ─► verifyFirebaseUser_ (Google Identity Toolkit)
                               ─► read profiles/{uid} with the user's token
                               ─► status must be 'active'; country not in the restricted list
                               ─► per-user daily counter (AI_USER_DAILY_LIMIT, default 10)
                               ─► global daily counter (AI_DAILY_LIMIT, default 40)
                               ─► Gemini call with the key from Script Properties

إذا فشل التحليل يُعاد العدّاد اليومي للمستخدم. ولا يُرسل مفتاح Gemini إلى الجهاز إطلاقًا.

5.4 مزامنة الـ Hub الخاصة بالمالك

كل إجراءات الـ Hub (ping، foods، push، pull، saveFoods، backup، meta، analyzeMeal، aiDiag، setAiKey، setCloudConfig) تتطلب APP_TOKEN مطابقًا تمامًا، وإلا كان الرد unauthorized. وتُفحص التغييرات أيضًا (جداول معروفة فقط، وطول المفتاح ≤ 200، والحمولة ≤ 45,000 حرف، و≤ 500 تغيير في الطلب الواحد).

6. تعيين المشرفين

  • تنص القواعد على allow write: if false للمسار admins/{uid}: لا يستطيع أحد أن يصبح مشرفًا من داخل التطبيق، ولا حتى المشرفون الحاليون.
  • ينشئ المالك مشرفًا بتشغيل node scripts/laptop-setup.mjs --cloud <e-mail> بعد التسجيل في التطبيق؛ فيكتب السكربت admins/{uid} عبر واجهة Firestore REST ببيانات اعتماد Google الخاصة بالمالك (أو يستخدم المالك وحدة تحكم Firebase).
  • الوضع في 10 نوفمبر 2026: لا يوجد مشرف بعد — بانتظار تسجيل المالك وإعادة تشغيل الأمر.
  • إزالة مشرف: حذف admins/{uid} من وحدة تحكم Firebase (لا توجد وظيفة لذلك داخل التطبيق).

7. قرارات التصميم وحدودها

القرارالسبب / الأثر
Firestore بدلًا من Google Sheets لبيانات المستخدمين المتعددينلا توفر Sheets أمانًا على مستوى الصف، وكل طلب سيعمل بهوية المالك (docs/ARCHITECTURE.md)
بيانات الأدوار في مستندات Firestore لا في المطالبات المخصصة (custom claims)تعمل على خطة Spark المجانية دون شيفرة خادم؛ وكل تقييم للقواعد يجري عمليات بحث عن مستندات (exists/get) تُحتسب ضمن حصة القراءات
فحص الحالة في كل قاعدة للبيانات الخاصةيسري الإيقاف على الخادم فورًا؛ والأثر الجانبي: المستخدم الموقوف لا يستطيع أيضًا حذف سجلاته
نشر Apps Script بإتاحة «لأي شخص»لا يستطيع تطبيق PWA إرسال ملفات تعريف دخول Google؛ وتعتمد الحماية على فحص الرمز ورمز الهوية
عدم فرض التحقق من البريدتُرسل رسالة تحقق لكن لا التطبيق ولا القواعد تفحص email_verified (انظر MEGO_Security_Audit_and_Known_Risks)
لا مصادقة متعددة العوامل (MFA)غير منفذة في الشيفرة
