Purpose and scope

This document describes the architecture behind who a caller is (authentication) and what that caller may do (authorization) in MEGO. It names every identity mechanism, every enforcement point and every role, and explains where each decision is actually made. Step-by-step session behaviour (registration screens, sign-out, password reset) is covered in MEGO_Authentication_and_Session_Management; the line-by-line Firestore rules are in MEGO_Access_Control_and_Permissions. No secret value appears in this document; secrets are named only.

1. Architecture overview

MEGO is a static Progressive Web App served from GitHub Pages. It has no application server of its own. Authentication and authorization therefore rely on two Google services that enforce rules on their own servers, plus one owner-operated Apps Script web app.

 Phone / browser (PWA, untrusted client)
   │
   ├── Firebase Authentication (Email/Password) ──► issues a short-lived ID token
   │         │
   │         ▼
   ├── Cloud Firestore ──► firebase/firestore.rules evaluated by Google on every request
   │                        (identity = request.auth.uid, role data = profiles/, admins/)
   │
   └── Apps Script web app (apps-script/Code.gs, runs as the owner)
             ├─ owner/guest device: shared secret APP_TOKEN (Script Properties)
             ├─ signed-in user (AI scanner only): Firebase ID token → verified with Google
             │     Identity Toolkit, then profile read WITH THE USER'S TOKEN (rules apply)
             └─ one-time install: bootstrap secret checked against a SHA-256 hash

Principle: the browser is never trusted. Buttons that are hidden in the user interface (for example the admin dashboard) are a convenience only; every real decision is taken by Firestore rules or by the Apps Script doPost handler.

Roles are independent: an administrator is also a normal user for their own private data, and the administrator role gives no access to anyone's private records.

4. Enforcement points

#Enforcement pointDecidesTrusted?
4.1Firebase AuthenticationPassword check, account uniqueness, token issuance, rate limiting of sign-in attempts (too-many-requests)Yes (Google)
4.2Firestore security rules (firebase/firestore.rules)Every read/write of profiles, private records, shared foods, submissions, error reportsYes (Google)
4.3Apps Script doPostToken check for Hub actions; ID-token check, active-profile check, country check and daily limits for the AI proxy; admin check for aiStatsYes (runs in the owner's Google account)
4.4Client (account.ts, Account.tsx)Which screen is shown (welcome, suspended, admin), which local database is openedNo — convenience only

The Apps Script AI proxy reads profiles/{uid} and admins/{uid} through the Firestore REST API with the user's own ID token, so the same Firestore rules apply to the proxy as to the app; the proxy holds no Firestore super-user credential.

5. Authorization flows

5.1 Signed-in user reads or writes own data

  1. The app writes users/{uid}/{table}/{key} with the SDK; the ID token is attached automatically.
  2. Firestore checks: request.auth.uid == uid, a profile exists with status active, the record shape is valid, and for updates updatedAt does not go back.
  3. Any failure returns permission-denied. The sync code treats a denied write as a conflict (the server already holds a newer copy, or the account is suspended).

5.2 Administrator actions

  1. At start-up watchSession() calls isAdmin(uid): true if admins/{uid} can be read (only the user themself may read it).
  2. The dashboard calls adminStats (counts), adminListProfiles, adminSetStatus, adminListErrors, adminListSubmissions, adminReview, publishSharedFoods. Each call is checked again by the rules (isAdmin()); a non-admin who forces the screen open receives 403.

5.3 AI scanner for a signed-in user

app ──(idToken, image)──► doPost ─► verifyFirebaseUser_ (Google Identity Toolkit)
                               ─► read profiles/{uid} with the user's token
                               ─► status must be 'active'; country not in the restricted list
                               ─► per-user daily counter (AI_USER_DAILY_LIMIT, default 10)
                               ─► global daily counter (AI_DAILY_LIMIT, default 40)
                               ─► Gemini call with the key from Script Properties

A failed analysis refunds the per-user counter. The Gemini key is never sent to the device.

5.4 Owner Hub sync

Every Hub action (ping, foods, push, pull, saveFoods, backup, meta, analyzeMeal, aiDiag, setAiKey, setCloudConfig) requires the exact APP_TOKEN; otherwise the response is unauthorized. Changes are additionally validated (known tables only, key length ≤ 200, payload ≤ 45,000 characters, ≤ 500 changes per request).

6. Administrator provisioning

  • The rules contain allow write: if false for admins/{uid}: nobody can become administrator from the app, including existing administrators.
  • The owner creates an administrator by running node scripts/laptop-setup.mjs --cloud <e-mail> after registering in the app; the script writes admins/{uid} through the Firestore REST API with the owner's Google credentials (or the owner uses the Firebase console).
  • Status 10 Nov 2026: no administrator exists yet — waiting for the owner to register and re-run the command.
  • Removing an administrator: delete admins/{uid} in the Firebase console (no in-app function).

7. Design decisions and limits

DecisionReason / consequence
Firestore instead of Google Sheets for multi-user dataSheets has no row-level security; every request would run as the owner (docs/ARCHITECTURE.md)
Role data in Firestore documents, not custom claimsWorks on the free Spark plan without server code; each rule evaluation performs document lookups (exists/get), which count toward Firestore read quotas
Status check on every private-data ruleSuspension takes effect on the server immediately; consequence: a suspended user also cannot delete their own records
Apps Script deployed "access: anyone"A PWA cannot send Google login cookies; protection rests on the token / ID-token checks
E-mail verification not enforcedA verification e-mail is sent but neither app nor rules check email_verified (see MEGO_Security_Audit_and_Known_Risks)
No multi-factor authenticationNot implemented in the code
