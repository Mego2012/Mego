Purpose and scope

This document describes every place where MEGO stores structured data and how the stores relate to each other: the on-device IndexedDB database (Dexie), the Cloud Firestore collections used by signed-in accounts, and the tabs of the owner's Google Sheet "MEGO Nutrition Hub" managed by the Apps Script backend. All table names, keys, indexes and fields were taken from the source code: src/lib/db.ts, src/lib/types.ts, src/lib/firebase.ts, src/lib/cloudSync.ts, firebase/firestore.rules and apps-script/Code.gs.

2. Local database (IndexedDB / Dexie)

2.1 Version history

Dexie versionChange
1Tables foods, foodChanges, entries, recipes, templates, plans, plannedDays, body, days, settings, outbox
2Additive only: new tables kv, fasts, photos, backups. Existing records are not transformed.

DB_SCHEMA_VERSION = 2. Before Dexie upgrades an existing database, preMigrationBackup() copies every store of the old version as JSON (format mego-nutrition-backup) into the separate database mego-nutrition-premigration. Dexie stores version × 10 in native IndexedDB, which the function takes into account.

4. Cloud Firestore collections

No composite indexes are defined (firebase/firestore.indexes.json is empty); queries use single-field indexes.

PathFieldsWritten by
profiles/{uid}displayName, email, status ('active'|'suspended'), country (2 letters), ageConfirmed (true), createdAt, lastActiveAtOwner at registration; owner may change displayName, country, lastActiveAt; admin may change status only
users/{uid}/{table}/{key}data (JSON string < 300,000 chars), updatedAt (int), deleted? (bool) — no other fields allowedOnly the owner while active; table must be one of the 12 synced tables
admins/{uid}since (timestamp number)Never from the app (rules: write: if false); written with owner credentials by scripts/laptop-setup.mjs --cloud <email>
foods/{id}row, sheetKey, nameAr, nameEn, category, per100, pieceGrams?, state, stateLabel, prep, notesAdmins only (publish verified foods, approve submissions as U-<submissionId>)
foodSubmissions/{id}ownerUid, status ('pending'|'approved'|'rejected'), at, food {…}Users create as pending with their own uid; admins review
errorReports/{id}at, kind (≤ 40 chars), message (< 500 chars), appAny signed-in user; read only by admins

The settings record is uploaded without its sync block (serialise() in cloudSync.ts). Shared foods arrive locally with source: 'sheet' and are not pushed back to users/…/foods.

6. Relationships and data flow

 Food (id) ──< DiaryEntry.foodId        (entry keeps its own basis snapshot)
 Food (id) ──< RecipeIngredient.foodId ── Recipe (id) ──< DiaryEntry.recipeId
 Food/Recipe ──< PlanItem ── MealTemplate / DayPlan (id) ──< PlannedDay.planId
 Food (id) ──< FoodChange.foodId
 DayLog.date ·· DiaryEntry.date ·· BodyEntry.date   (joined by calendar date)

 ┌──────────── device ─────────────┐        ┌───────── Firestore ─────────┐
 │ mego-u-<uid>  12 SYNC_TABLES ───┼─outbox─▶│ users/{uid}/{table}/{key}   │
 │               ◀── live listener ─┼────────│                             │
 │ photos, backups (local only)     │        │ profiles/{uid}  admins/{uid}│
 │ foods(source=sheet) ◀────────────┼────────│ foods/{id} (shared)         │
 └──────────────────────────────────┘        │ foodSubmissions  errorReports│
 ┌──── owner device (mego-nutrition) ┐        └─────────────────────────────┘
 │ 12 SYNC_TABLES ── push/pull ──────┼──▶ Apps Script ──▶ Hub tabs (Food_Log …)
 └───────────────────────────────────┘

Relations are logical (by id), not enforced foreign keys. Deleting a food does not cascade: foods are archived (archived), and diary entries remain valid because they carry their own nutrition snapshot. Conflict rule everywhere: a record with an older updatedAt never overwrites a newer one (Firestore rule, Hub push_, and local applyRemote).

7. Verification status

  • Verified live (production): Firestore records written under users/{uid}/entries for the owner, cross-account and anonymous reads refused (403), second-device sync — scripts/live-verify.mjs 14/14. Hub tabs Food_Database (160 foods), soft delete into Deleted_Records and "older copy never overwrites newer" — laptop-setup live tests.
  • Tested on emulators: record shape validation (data string, size limit, unknown table refused) — tests-rules/rules.test.ts; conflict handling — tests-rules/cloud.test.ts.
  • Not verified: the automatic pre-migration backup has not been checked during a real upgrade on a real user's device.
