Purpose and scope

This document explains, rule by rule, the Firestore security rules in firebase/firestore.rules — the central access-control mechanism of MEGO — and summarises the permissions enforced by the Apps Script backend and the client. It includes a complete permission matrix, the test that covers each rule, the known gaps of the rules and the procedure for changing them safely.

1. Principles

  • Default deny: any path not matched by a rule is refused (Firestore behaviour).
  • Server enforcement: Google evaluates the rules on every request; the app cannot bypass them.
  • Owner only, active only: private data is reachable only by its owner and only while the owner's profile has status == 'active'.
  • Least privilege for admins: admins manage account status and shared foods, but cannot read private records.
  • Monotonic updates: an older copy can never replace a newer one.

Note: rules apply to client SDK/REST requests made with user tokens. The project owner's Google Cloud credentials (console, setup script) are not limited by these rules.

2. Full rules text

Deployed version as in the repository (rules_version = '2'):

rules_version = '2';
// MEGO — Firestore security rules (enforced by Google's servers on every request).
//  * users/{uid}/**  : private data. Only the owner, only while the account is active. Admins have NO access.
//                      An older copy can never overwrite a newer one (updatedAt must not go back).
//  * profiles/{uid}  : account card (name, email, status, country, lastActiveAt). Owner reads/creates/updates a
//                      fixed set of fields; admins read all and may change ONLY the status.
//  * admins/{uid}    : admin list. Readable by that user only. Written only from the Firebase console / setup script.
//  * foods/{id}      : shared verified food database. Any signed-in active user reads; only admins write.
//  * foodSubmissions : users propose foods; owner and admins read; admins review.
//  * errorReports    : users may create small error reports (no personal data); only admins read.
service cloud.firestore {
  match /databases/{database}/documents {
    function signedIn() { return request.auth != null; }
    function isAdmin() { return signedIn() && exists(/databases/$(database)/documents/admins/$(request.auth.uid)); }
    function profile(uid) { return get(/databases/$(database)/documents/profiles/$(uid)); }
    function isActive() {
      return signedIn() && exists(/databases/$(database)/documents/profiles/$(request.auth.uid))
        && profile(request.auth.uid).data.status == 'active';
    }
    function isOwner(uid) { return signedIn() && request.auth.uid == uid; }

    match /users/{uid}/{table}/{key} {
      allow read: if isOwner(uid) && isActive();
      allow create: if isOwner(uid) && isActive() && validRecord();
      allow update: if isOwner(uid) && isActive() && validRecord()
        && request.resource.data.updatedAt >= resource.data.updatedAt;
      allow delete: if isOwner(uid) && isActive();
      function validRecord() {
        return request.resource.data.keys().hasOnly(['data', 'updatedAt', 'deleted'])
          && request.resource.data.updatedAt is int
          && request.resource.data.data is string && request.resource.data.data.size() < 300000
          && (!('deleted' in request.resource.data) || request.resource.data.deleted is bool)
          && table in ['entries', 'body', 'days', 'recipes', 'templates', 'plans', 'plannedDays', 'fasts', 'kv', 'settings', 'foodChanges', 'foods'];
      }
    }

    match /profiles/{uid} {
      allow read: if isOwner(uid) || isAdmin();
      allow create: if isOwner(uid)
        && request.resource.data.keys().hasOnly(['displayName', 'email', 'status', 'country', 'ageConfirmed', 'createdAt', 'lastActiveAt'])
        && request.resource.data.status == 'active' && request.resource.data.ageConfirmed == true
        && request.resource.data.email == request.auth.token.email;
      allow update: if (isOwner(uid) && profile(uid).data.status == 'active'
          && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['displayName', 'country', 'lastActiveAt']))
        || (isAdmin() && request.resource.data.diff(resource.data).affectedKeys().hasOnly(['status'])
          && request.resource.data.status in ['active', 'suspended']);
      allow delete: if isOwner(uid);
    }

    match /admins/{uid} {
      allow read: if isOwner(uid);
      allow write: if false;
    }

    match /foods/{id} {
      allow read: if isActive();
      allow write: if isAdmin();
    }

    match /foodSubmissions/{id} {
      allow read: if isAdmin() || (isActive() && resource.data.ownerUid == request.auth.uid);
      allow create: if isActive() && request.resource.data.ownerUid == request.auth.uid && request.resource.data.status == 'pending';
      allow update: if isAdmin();
      allow delete: if isAdmin() || (isActive() && resource.data.ownerUid == request.auth.uid && resource.data.status == 'pending');
    }

    match /errorReports/{id} {
      allow create: if signedIn() && request.resource.data.keys().hasOnly(['at', 'kind', 'message', 'app'])
        && request.resource.data.message is string && request.resource.data.message.size() < 500;
      allow read, delete: if isAdmin();
    }
  }
}

4. Private data: users/{uid}/{table}/{key}

OperationCondition
read (get, list)isOwner(uid) && isActive()
createowner, active, validRecord()
updateowner, active, validRecord(), and request.resource.data.updatedAt >= resource.data.updatedAt
deleteowner, active

validRecord() requires:

  • only the keys data, updatedAt, deleted;
  • updatedAt is an integer;
  • data is a string shorter than 300,000 characters (the record is stored as JSON text);
  • deleted, if present, is a boolean;
  • table is one of 12 names: entries, body, days, recipes, templates, plans, plannedDays, fasts, kv, settings, foodChanges, foods.

How the app uses it: src/lib/cloudSync.ts writes each local change with setDoc. A deletion is written as a tombstone {data: '{}', updatedAt, deleted: true} (an update, so other devices learn about it); hard delete is used only during account deletion. A permission-denied answer is counted as a conflict: the server already holds a newer copy, or the account is suspended.

Example: device A (offline) edits entry e1 at time 100; device B edits it at time 200 and syncs first. When A reconnects, its write with updatedAt = 100 is refused; A then receives B's version through the live listener.

5. Profiles: profiles/{uid}

Consequences: a user cannot change their e-mail or status, cannot reactivate themselves, and an admin cannot rename users or set any status other than active/suspended.

6. Admins: admins/{uid}

  • read: only the user whose uid it is (the app uses this to detect the admin role);
  • write: false for everyone — created only with owner credentials (setup script --cloud or Firebase console).

8. Error reports: errorReports/{id}

  • create: any signed-in user; keys only at, kind, message, app; message is a string shorter than 500 characters;
  • read and delete: admins; update: nobody.

12. Known gaps in the rules

  • Owner profile updates do not validate the type or length of displayName or country (the app trims the name to 40 characters). Because country is editable and self-declared, the AI region restriction relies on user honesty.
  • foodSubmissions creation validates only ownerUid and status, not the food fields.
  • errorReports may be created by any signed-in user, including suspended ones; only the message length is limited.
  • A suspended user cannot delete their private records (delete requires isActive()), only their profile.
  • email_verified is not checked anywhere.

These are tracked in MEGO_Security_Audit_and_Known_Risks.

13. Changing the rules

  1. Edit firebase/firestore.rules on a branch.
  2. Add or update tests in tests-rules/ and run npm run test:rules (emulators) — all must pass.
  3. Deploy with the owner's credentials: node scripts/laptop-setup.mjs --cloud <e-mail> (runs firebase deploy --only firestore:rules,firestore:indexes) or the Firebase CLI directly.
  4. Run node scripts/laptop-setup.mjs --verify (live verification) and confirm all checks pass.
  5. Rollback: redeploy the previous version of the file from git.
