Purpose and scope

This document describes every backup mechanism that exists in MEGO, what each one contains and where it lives, and gives step-by-step recovery procedures for the realistic failure scenarios — including the storage-loss incident of 10 November 2026 and the fix that is now live. It merges the "Data Backup and Recovery" and "Backup and Recovery Procedures" topics into one document. The end-user view of the buttons is in MEGO_Backup_and_Export_Guide.

1. Backup layers overview

 Layer                     Where                                Protects against
 ───────────────────────── ──────────────────────────────────── ────────────────────────────────
 1 Local automatic backups  inside the device database (IndexedDB) bad import/restore, bad update
 2 Pre-migration snapshot   separate DB  mego-nutrition-premigration  schema upgrade problems
 3 Backup file (JSON)       user's Downloads / any storage       device loss (guest and account)
 4 Cloud sync (Firestore)   users/{uid}/... in me-central2       device loss (signed-in accounts)
 5 Hub + Drive copies       owner's Google Drive                 owner's data, Hub structure changes

Layers 1 and 2 live in the same browser storage as the data; they do not survive loss of that storage. Layers 3–5 do.

2. On-device automatic backups

Code: src/lib/localBackup.ts. A backup is a full JSON snapshot of all synced tables saved in the backups table of the current device database.

ReasonWhen
auto-dailyOnce per calendar day at app start, if there is data
pre-updateOnce per app release and database before the new release writes anything (current release id APP_RELEASE = '1.3-training')
pre-restoreBefore restoring a local backup or a backup file
pre-importBefore importing foods or data files
pre-pullBefore "Restore from sheet" (Hub)
manualSettings → "Back up now"

Rotation: the 10 most recent backups are kept; the 3 most recent pre-update backups are protected and never rotated out. Each signed-in account has its own backups inside mego-u-<uid>.

Pre-migration snapshot: before Dexie upgrades the schema, preMigrationBackup() (src/lib/db.ts) copies the old database into mego-nutrition-premigration. Settings lists these snapshots. Dexie schema is still version 2.

Data check: Settings → Data check (src/lib/dataCheck.ts, read-only) compares current record counts with the latest pre-update backup and reports "All records are intact" or "Some tables have fewer records…".

Backup files are not encrypted. They contain personal data and should be stored privately.

4. Cloud copy (signed-in accounts)

  • Every local change goes through an outbox and is written to users/{uid}/{table}/{key} in Firestore; other devices receive it through live listeners (src/lib/cloudSync.ts).
  • The cloud copy is a synchronised copy, not a versioned backup: a deletion or an edit is propagated to the cloud too. Deletions are stored as tombstones (deleted: true, empty data).
  • No scheduled Firestore export or point-in-time recovery is configured in this repository. Whether such features are available on the free Spark plan was not checked (Not verified).

5. Owner Hub backups (Google Sheets / Drive)

  • The original Excel Hub file is kept unchanged as the original backup; a dated copy "BACKUP MEGO Nutrition Hub — before migrateHub — …" was created on 7 Nov 2026.
  • backupHub_() makes a full Drive copy named "BACKUP MEGO Nutrition Hub — <reason> — <timestamp>" before migrations and, through backupOncePerDay_(), once per day before the first food write-back (saveFoods). Each backup is logged in the Backup_Log tab.
  • Deleted rows are copied into Deleted_Records (table, key, deleted_at, JSON, recovered) before removal — soft delete. Recovery from this tab is manual (copy the JSON back); there is no automatic undelete function.
  • Older copies never overwrite newer ones (timestamp check; conflicts reported).

6. What is not backed up

  • Progress photos (photos table): device only — not synced, not in backup files.
  • Pending outbox items (not yet uploaded changes) are not in backup files.
  • Guest data without a backup file or Hub connection: only on the device.
  • Firebase accounts themselves (logins) cannot be restored after deletion.

7. Restore behaviour

  1. The file is parsed; format must be mego-nutrition-backup; each table must be an array; every record must have its key; diary entries must have numeric calories. On any error nothing is written.
  2. A pre-restore backup of the current data is saved.
  3. Records are merged in one transaction: a backup record is written if it does not exist locally or its updatedAt is the same or newer. Nothing is deleted. Settings are replaced, but the device's sync configuration is kept.
  4. In account mode, restored records reach the cloud through the normal sync.

8. Recovery procedures by scenario

ScenarioProcedure
A. Signed-in user: phone lost, reset, new phone, or browser data clearedOpen the app → Sign in with the same e-mail and password → wait for the download (all synced tables return). Progress photos cannot be recovered.
B. Signed-in user: app shows the welcome screen unexpectedlySign in again with the same account. Since the 10 Nov fix, a missing local database triggers a full download. If data is still missing after a few minutes online, see section 9 and contact support.
C. Guest user: device data lostRestore from the latest backup file (Settings → "Restore from backup file"). Without a backup file the data cannot be recovered. Owner device with Hub: "Restore from sheet".
D. Wrong import or restoreSettings → Local backups → pick the pre-import / pre-restore backup → Restore. Note: restore merges, so records added by the wrong import remain and must be deleted manually.
E. Problem after an app updateSettings → Data check. If it reports fewer records, restore the pre-update backup from Local backups.
F. Problem after a schema upgradePre-migration snapshot in mego-nutrition-premigration (listed in Settings). Restoring it requires developer help (Not verified as an in-app action).
G. Hub sheet damagedOpen the latest "BACKUP MEGO Nutrition Hub — …" copy in Drive (File → Make a copy) or recover single rows from Deleted_Records. Then re-sync the owner device.
H. Accidental account deletionNot recoverable from the cloud; only from a backup file previously downloaded, imported into a new account.

9. Incident 10 Nov 2026: storage loss on an Android phone

9.1 What happened

On an Android phone, the browser lost the app's IndexedDB storage (all local records and the Firebase session) while localStorage survived. The app showed the welcome screen. After the user signed in again, the app stayed empty. The same had happened once before.

9.2 Root cause

  • The cloud listener started each table from a "last seen" marker kept in localStorage. Because the markers survived but the records did not, the listener only asked for records newer than the marker, so the older records were never downloaded again.
  • A fresh default settings record created on the empty device could outrank the saved settings in the cloud.

9.3 Fix (live; src/lib/cloudSync.ts, account.ts, repo.ts)

  • Markers renamed to mego.cloud2. — every device re-downloads its account in full once.
  • At start-up, if the account's local database is missing, the markers are reset (resetCloudMarkers).
  • An empty local table always downloads in full; settings are always re-read.
  • Untouched default settings (never saved by the user) never outrank the cloud copy.
  • One record that cannot be applied no longer stops the rest of the download (it is reported instead).
  • Weigh-ins with the same date: the newer one is kept on the device; the other stays untouched in the cloud.

9.4 Verification and lesson

Reproduced and verified on the Firebase emulators (e2e/storage-loss.mjs); the owner confirmed the data came back. Lesson for users: signed-in accounts are recoverable by signing in again; guest data lives only on the device — download backup files regularly.
