Purpose and scope

This document describes how each part of MEGO is updated safely and how a faulty update is reversed: the PWA on GitHub Pages, the user data on devices and in the cloud, the Apps Script backend (redeployed to the same deployment), the Google Sheet Hub and the Firestore rules. It explains which backups are taken automatically before an update and how to use them.

1. Safety principles

  • Updates never delete user data: restores and syncs merge (a record is replaced only by a copy whose updatedAt is the same or newer); the Hub and Firestore refuse older copies.
  • A backup is taken before every risky step (sections 2 and 7).
  • Backend redeploys keep the same deployment id, so the web-app URL and token do not change and no device needs to reconnect.
  • Prefer "roll forward" (a new fixing commit) over rewriting history.

3. Updating the app (PWA)

  1. Push the release (MEGO_Build_and_Release_Procedures); CI tests, builds and deploys.
  2. Devices load the new service worker (registerType: 'autoUpdate'); the new version is active from a following launch.
  3. On first start the pre-update backup is saved (if APP_RELEASE changed).
  4. Check: Settings → Data check compares current record counts (entries, body, days, foods) with the newest pre-update backup and says whether every table still has at least as many records; it also lists suspect per-serving foods and possible duplicates. It is read-only.

4. Rolling back the app

  1. Identify the faulty commit (git log --oneline).
  2. Create a reverting commit and push it: 
    git revert <commit>
git push origin claude/nutrition-tracking-app-989rku
  3. The workflow redeploys the previous code; installed apps update automatically.
  4. If data looks wrong on a device: Settings → Automatic backups on this phone → choose the pre-update backup → Restore (a pre-restore backup is taken first; restore merges and never deletes). Signed-in users can also sign in again: the cloud copy is downloaded (see the 10 Nov 2026 incident in MEGO_Data_Backup_and_Recovery).

Notes: data written by the newer version (e.g. in the kv table) stays on the device and in the cloud; whether an older version ignores it correctly was not tested. A reverted APP_RELEASE value does not create a new pre-update backup if one for that value already exists.

5. Updating the backend (same deployment)

cd $HOME\Mego        (Windows; on macOS/Linux: cd ~/Mego)
git pull
node scripts/laptop-setup.mjs --update-backend
  • Pushes the latest Code.gs + appsscript.json and runs clasp create-deployment --deploymentId <stored id>: same URL, same token, Script Properties (keys, limits, Hub id) untouched, Hub data untouched.
  • Ends with the AI diagnostic and prints the backend version (should be 8 for the current repository).
  • --hub-complete-foods does the same update, then adds library foods to the Hub (adds only; daily Drive backup first; repeat runs add nothing).
  • Optional: node scripts/laptop-setup.mjs --test for the full live test set.

6. Rolling back the backend

Option A — redeploy an older Code.gs to the same deployment:

git checkout <good commit> -- apps-script/Code.gs apps-script/appsscript.json
node scripts/laptop-setup.mjs --update-backend
git checkout HEAD -- apps-script/Code.gs apps-script/appsscript.json

Option B — Apps Script editor: Deploy → Manage deployments → Edit (pencil) → Version: choose an earlier version → Deploy (same URL). Each clasp create-deployment created a version, so earlier versions exist in the project.

After a rollback, app features that need a newer backend report an outdated backend (AI_OLD_BACKEND); --hub-complete-foods refuses to run below version 8.

7. Hub data recovery

  • Deleted records are soft-deleted into the Deleted_Records tab (table, key, deleted_at, json, recovered).
  • Drive backup copies (section 2) can be opened and compared; Google Sheets File → Version history can restore an earlier state of the Hub.
  • The original Excel file was never modified and remains the ultimate source backup.

8. Firestore rules and public config

  • Rules: revert the change in firebase/firestore.rules, run npm run test:rules, then node scripts/laptop-setup.mjs --cloud to redeploy (the command also re-runs the live verification).
  • Public config: public/firebase-config.json is a normal repository file; reverting it redeploys with the app. Without it the site runs in guest mode only.

9. Decision table

Symptom after an updateFirst action
Deploy run redNothing was published; fix and push again
Screen broken for everyoneRevert the commit (section 4)
Data missing on one deviceData check → restore pre-update backup, or sign in again (accounts)
AI scanner errors after backend updateRead the AI diagnostic; roll back the backend (section 6) if a code error
Hub values wrongCompare with the Drive backup / version history; restore
Live verifier shows 403 where access is expectedRoll back the rules (section 8)
