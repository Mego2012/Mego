Purpose and scope

This document describes how MEGO's components are tested together: the app with Firebase (Auth, Firestore and the security rules) on the official emulators, the app with the Apps Script backend through an emulated Google environment, the laptop-setup script against the real backend code, the v1→v2 upgrade and the storage-loss recovery scenario (e2e/storage-loss.mjs) that reproduces the incident of 10 November 2026. The multi-user browser suite is described in MEGO_Multi_User_Testing.

2. Firestore rules and cloud sync (tests-rules/)

Run with npm run test:rules, which executes firebase emulators:exec --project demo-mego --only firestore,auth "vitest run --config vitest.rules.config.ts". The config runs files one after another (fileParallelism: false) with 30-second timeouts and reuses tests/setup.ts.

2.2 cloud.test.ts — 4 tests (real app sync code + Firebase SDK)

  • Registration creates an active profile; age confirmation is required.
  • Each user logs on their own device database; records land only under their own uid.
  • A second device of the same user receives the data live; other users' data never appears.
  • An older copy from an offline device does not overwrite the newer one.

4. Storage-loss recovery scenario (e2e/storage-loss.mjs)

Background: on 10 November 2026 an Android phone lost its IndexedDB (records and Firebase session) while localStorage survived. After signing in again the app stayed empty because the cloud listener resumed from "last seen" markers kept in localStorage, and a fresh default settings record outranked the saved settings. It had happened once before. Fixes are in src/lib/cloudSync.ts, account.ts and repo.ts (see MEGO_Known_Bugs_and_Limitations).

4.1 Steps performed by the script

  1. Starts vite preview on port 4192 and a Chromium context emulating a Pixel 7 (English).
  2. Registers a disposable account (country, age 18+ and terms confirmed, weight 80, calorie target 2110).
  3. Creates a custom food from the search box, logs 200 g of it for lunch and waits for the outbox to reach the cloud.
  4. Seeds the cloud directly (as a user who re-entered data after an earlier loss): an old diary entry and two weigh-ins for the same date with different updatedAt (80.4 older, 80.1 newer).
  5. Simulates the incident: deletes every IndexedDB database in the page; localStorage is kept.
  6. Reloads: the welcome screen must appear. Signs in with the same account.
  7. Checks after 8 s: at least 2 diary entries, calorie target still 2110, the custom food visible in the diary, and the weigh-in for that date = the newer copy (80.1).
  8. Prints RESULT: data recovered and exits 0, otherwise exits 1 and saves e2e/storage-loss-fail.png.

4.2 Expected behaviour verified

  • Markers renamed to mego.cloud2. — every device re-downloads its account once.
  • A missing local database resets the markers; an empty table downloads in full; settings are always re-read.
  • Untouched defaults (updatedAt 0) never outrank the cloud copy (also unit-tested in tests/cloud-recovery.test.ts).
  • One bad record never stops the download; same-date weigh-ins keep the newer one.

Run (after npm run build): firebase emulators:exec --project demo-mego --only firestore,auth "node e2e/storage-loss.mjs". There is no npm script for it.

5. Apps Script backend integration (gas-mock)

e2e/gas-mock.mjs loads the real apps-script/Code.gs and provides in-memory versions of SpreadsheetApp, DriveApp, PropertiesService, LockService, UrlFetchApp and Utilities. It is used by the unit suite (Hub and scanner tests), the browser suite (requests to the backend URL are routed to it) and the multi-user suite (AI proxy). It covers authorization by token, Hub ID pinning, Excel→native conversion with the original untouched, push/pull, conflicts, soft delete into Deleted_Records, and the Gemini call path with scripted responses. Google's real services are not contacted.

6. Laptop setup and upgrade scenarios

6.1 e2e/laptop-setup-test.mjs — 10 checks

Runs the real scripts/laptop-setup.mjs against Code.gs served over local HTTP. Checks: script exit code 0; bootstrap converted and switched to the native Hub; original Excel untouched; all live checks passed; 160 foods reported; AI photo analysis went through the backend to the Gemini endpoint only; the MEGO-TEST record cleaned up; state file private (mode 600) and outside the repository; connect link printed; bootstrap cannot run twice. It uses the private 160-food table when present, otherwise the synthetic fixture.

6.2 e2e/hub-complete-test.mjs — 9 checks

Runs scripts/laptop-setup.mjs --hub-complete-foods twice against the real Code.gs on an emulated native Hub. Checks: both runs exit 0; ready meals added (all recipes whose ingredients have values); every existing cell unchanged except empty English names; existing English names never replaced; English names present for all original foods; meal rows have positive values and a serving weight; the second run adds nothing; a daily Drive backup is taken before writing; the first meal is the recipe library's first recipe.

6.3 e2e/migration-test.mjs — upgrade v1 → v2

Serves a v1 build, imports the sample sheet and logs 200 g raw chicken; then serves the v2 build on the same origin and profile. It prints a JSON report (calories shown before/after, new UI present, pre-migration backup database mego-nutrition-premigration with entry/food counts). Requires the global http-server; the report is read by a person (no automatic pass/fail).

  • Verified live: the same rules and sync paths through scripts/live-verify.mjs 14/14 on 7 Nov 2026; the 10 Nov fix is deployed on the live site.
