Purpose and scope

This document is the honest register of MEGO's defects and limits as of 10 November 2026: open bugs, bugs that were found and fixed (with dates, cause and fix — so that the same failure is recognised if it returns), the incident of 10 November 2026, and the limitations that remain by design or because a step is still pending. It contains no personal data.

3. Incident of 10 November 2026 — data not restored after the browser lost its local database

ItemDetails
SymptomOn an Android phone the app suddenly showed the welcome screen. After signing in again with the same account the diary was empty and the calorie target was the default 2000.
TriggerThe browser lost the app's IndexedDB (all local records and the Firebase session) while localStorage survived. It had happened once before; the first time the user re-entered data manually, so the cloud then held both copies.
Root causes(1) The cloud listener resumed from "last seen" markers kept in localStorage, so older records were never downloaded into the new, empty database. (2) A fresh default settings record had updatedAt = now and outranked the account's saved settings.
Fix (commits 114c128 and 5e872a8, live)Markers renamed to mego.cloud2. — every device re-downloads its account once; a missing local database resets the markers; an empty table always downloads in full; settings are always re-read; untouched defaults (updatedAt 0) never outrank the cloud copy; each record is applied on its own, so one bad record never stops the download; two weigh-ins for the same date keep the newer one (the other stays untouched in the cloud); Settings → Data check lists diary items and own foods that appear more than once (read-only, nothing removed). Changes in src/lib/cloudSync.ts, account.ts, repo.ts, dataCheck.ts.
VerificationReproduced and verified on the emulators with e2e/storage-loss.mjs (including old + re-entered copies); unit tests in tests/cloud-recovery.test.ts; the owner confirmed the data came back on the phone.
Lesson for usersSigned-in accounts are recoverable by signing in again. Guest data lives only on the device — guests should export backups regularly (MEGO_Backup_and_Export_Guide).
Not knownWhy the browser removed IndexedDB (storage pressure, browser cleanup, or another cause) — Not verified.

6. Remaining limitations — by design or external

  • Gemini free tier: can be slow at peak times (≈ 64 s in the 10 Nov live run) and can return overload or quota errors; only free Flash models are allowed, never a paid one. Default limits in Code.gs: 10 scans per user per day and 40 per day overall (owner-configurable within bounds); the values configured live are Not verified.
  • AI results are estimates: the scanner never auto-saves; the user must review; matched foods use database values.
  • Firebase Spark (free) limits apply to reads, writes and storage; behaviour near the limits is not tested.
  • Guest mode: data exists only on the device; if the browser clears its storage, guest data is lost unless exported.
  • Browser storage can be cleared by the browser or the system (as in the incident); signed-in accounts recover from the cloud.
  • Duplicates after re-entry are reported by Data check but never removed automatically; the user decides.
  • Same-date weigh-ins: the device keeps one per date (the newer); the other copy remains in the cloud.
  • Missing reference data is never invented: labneh has no verified USDA match, so recipes containing it stay incomplete; foods without amino-acid data are ranked in a partial-data group.
  • Food values come from the user's table, USDA or Open Food Facts as they are; four placeholder rows (0/0/0/0) in the owner's table cannot be logged until values are entered.
  • Cardio calories are MET-based estimates; the training coach is local rule-based logic, not AI.
  • Barcode camera scanning needs the browser's BarcodeDetector API; otherwise the code is typed.
  • Photos exist for 74 common foods; other foods show a drawn placeholder; recipes have no dish photos.
  • Password-reset e-mail delivery depends on Firebase and the user's mail provider (may land in spam).

7. Testing gaps

  • No recorded physical-device test; camera, barcode hardware and install not formally verified.
  • The full 57-check browser suite has not been recorded against the live URL (44/44 was, on 7 Nov).
  • The newest scripts/live-verify.mjs (with recipe, cardio and workout checks) has no recorded production run; the last recorded production run is 14/14 (7 Nov).
  • Open Food Facts is mocked in tests; no load testing; no code-coverage measurement.

8. Verification status

  • Verified: incident cause and fixes in the commit history and code; unit suite 199/199 run on 10 Nov 2026; live AI analysis and the owner's confirmation of data recovery (per the documentation brief).
  • Tested on emulators: storage-loss recovery scenario.
  • Not verified: the reason the browser deleted IndexedDB; live AI quota settings; behaviour on a range of Android devices.
