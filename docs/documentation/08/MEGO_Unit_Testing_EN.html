Purpose and scope

This document describes MEGO's unit test suite: the tool and configuration, every test file in tests/ with its test count and what it covers, the fixtures it uses, how it runs in CI and how to add tests. It reflects a real run of npx vitest run on 10 November 2026: 14 test files, 199 tests, all passed.

4. Test techniques used

  • Real modules, in-memory database: repository functions (addFoodEntry, saveSettings…) write to Dexie on fake-indexeddb exactly as in the browser.
  • Real backend in an emulator: e2e/gas-mock.mjs loads apps-script/Code.gs and emulates SpreadsheetApp, DriveApp, PropertiesService, LockService and UrlFetchApp.
  • Scripted external services: Gemini responses and errors (500, 503, 504, 400, 429) are scripted; Open Food Facts is mocked; no test calls an external service.
  • Exact numbers: e.g. roundMacros(e.macros) must equal { kcal: 120, protein: 23, carbs: 0, fat: 2.6 }.
  • Negative tests: what must never happen (auto-applying recommendations, filling missing data, paid AI models, removing duplicates automatically).

5. Running the suite and reading the output

npm test                     # whole suite
npx vitest run tests/core.test.ts          # one file
npx vitest run -t "TEST 1"                 # tests whose name matches

Expected summary: Test Files 14 passed (14) and Tests 199 passed (199). The scanner tests deliberately print lines such as Gemini gemini-3.8-flash → 503 … on stderr — these are the scripted error scenarios, not failures. The full run took about 7 seconds.

6. Writing a new unit test

  1. Put the file in tests/ with the suffix .test.ts.
  2. Call useDatabase('a-unique-name') in beforeEach when the test touches the database.
  3. Use fixtures from tests/fixtures/; never commit personal data. Guard tests that need the private table with it.skipIf.
  4. Assert exact values and add at least one "must not happen" assertion.
  5. Run npm test and npx tsc -b before committing; CI blocks deployment if a test fails.
