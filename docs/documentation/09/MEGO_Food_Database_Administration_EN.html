Purpose and scope

This document describes how the food data that MEGO offers to all users is administered: the owner's Google Sheets Hub (Food_Database tab), the shared Firestore collection /foods that every signed-in user receives, the review of user food suggestions and the built-in USDA reference database. It gives the procedures, preconditions and known limitations for each. Personal foods that a user creates for themself are not administered centrally and are out of scope. Sources: apps-script/Code.gs, src/lib/sync.ts, src/lib/sheetImport.ts, src/lib/cloudSync.ts, src/lib/firebase.ts, src/pages/Account.tsx, src/pages/Settings.tsx, scripts/build-food-db.mjs, firebase/firestore.rules.

Status note: no administrator account exists yet (10 November 2026), so publishing to /foods and reviewing submissions have not been carried out in production.

2. The Hub Food_Database (owner's Google Sheet)

The Hub was converted once from the original Excel file into a native Google Sheet; the original Excel file and the original food tab «قاعدة بيانات الأطعمة» are never modified. migrateHub() copied the original tab into Food_Database with stable IDs F0001…; the live check on 7 Nov 2026 reported 160 foods and 0 unreadable values.

2.1 Columns

food_id, name_ar, name_en, category, kcal_100g, protein_100g, carbs_100g, fat_100g, fiber_100g, sugar_100g, sodium_mg_100g, piece_g, state, state_label, prep, source, verification, barcode, notes, active, followed by two technical columns updated_at and json.

2.2 Rules applied when a device reads the tab

  • Required columns: food_id, name_ar, kcal_100g, protein_100g, carbs_100g, fat_100g; if one is missing the import stops with "missingColumns".
  • Rows without food_id or with active = no are skipped.
  • A missing or negative kcal/protein/carbs/fat value marks the food incomplete (it is imported but flagged); all-zero macros are reported as "zeroValues".
  • Values are per 100 g of the food in the stated state (raw / cooked / other).

2.3 Ownership and safety

  • Food_Database is owned by the sheet: the owner manages values there; devices pull them.
  • Edits made in the app to Hub foods are written back only if "Write food edits back to the Google Sheet" is enabled on that device (saveFoods). The backend rejects a batch of more than 200 foods, a food without a name and any kcal/protein/carbs/fat value outside 0–1000, and makes a full Drive backup copy of the Hub once per day before the first write-back.
  • Every write is timestamp-checked: an older copy never overwrites a newer row (conflict). Deleted rows are copied to Deleted_Records first.

3. Procedure: changing foods in the Hub

  1. Open the Hub in Google Sheets → tab Food_Database. Do not edit the original Arabic tab or the json / updated_at columns.
  2. Correct a value: edit the readable cells of the row (e.g. kcal_100g), keep food_id unchanged.
  3. Add a food: append a row with a new unique food_id in the same pattern (next free F####), Arabic name, state and the four main values per 100 g; fill notes/verification with the source.
  4. Retire a food: set active to no. (Devices that already have the food keep their local copy — the import never deletes local records.)
  5. On the owner's device: Settings → card "MEGO Nutrition Hub — sync & backup" → Import foods from sheet. The result shows how many foods were added, updated and unchanged.
  6. If the change must reach signed-in users, continue with section 5.

Note: the steps for hand-editing rows follow from the import code; editing rows directly in the sheet has not been exercised by an automated test (Not verified).

3.1 Bulk completion of the Hub: --hub-complete-foods (backend v8)

Since 10 Nov 2026 the owner can add the foods that the recipe library needs to the Hub in one command: node scripts/laptop-setup.mjs --hub-complete-foods. It first uploads and redeploys the current backend (same URL), then:

  1. Checks that the backend is version 8 or newer and that the Hub uses the structured Food_Database tab; otherwise it stops without writing.
  2. Ingredients: for each of the 69 recipe-library ingredients (public/fooddb/library-recipes.json) whose Arabic name is not yet an active Hub row, it adds a row with id LIB-ING-<hash>, category «مكوّنات الوصفات», source usda and the hand-checked USDA FoodData Central values. An ingredient without a verified reference (currently labneh, «لبنة») is never estimated; it is listed as a warning.
  3. Ready meals: for each of the 101 library recipes not yet in the Hub, it adds a row with id LIB-<recipe id>, category «وجبات (مكتبة الوصفات)», state cooked, computed from the Hub's own per-100 g values of the ingredients (USDA only where the Hub had nothing): per 100 g of raw ingredients, piece weight = 1 serving = total grams ÷ servings. A meal with any ingredient lacking usable values is skipped and listed.
  4. Rows are sent through saveFoods in batches of 100 (daily Drive backup of the Hub before the first write of the day).
  5. English names: the new action fillFoodNames writes name_en only where that cell is empty, using the hand-translated dictionary public/fooddb/food-names.json (160 names) plus the recipe names; every other cell and every existing name stays unchanged. The result reports "English names filled: N".

Existing rows and values are never changed and a second run adds nothing (tested 9/9 in e2e/hub-complete-test.mjs against the real Code.gs on an emulated Google backend). A live run on the owner's Hub is Not verified. After the run, import the foods on the owner's device (step 5 above).

The app offers the same completion for a user's own food list (Foods page: "Complete my food database" with a preview, local backup first, adds only, and "Arabic & English names", which fills only missing names, never changing an existing one); those foods are personal, not shared.

5. Procedure: publishing verified foods to the shared /foods database

5.1 What the button does

Administration → card Shared food database → Publish verified foods. The app takes the foods in the local database of the device it runs on that have source = "sheet", are not archived and are not incomplete, and writes each one to foods/{id} with the fields row, sheetKey, nameAr, nameEn, category, per100, pieceGrams, state, stateLabel, prep, notes. The id is the Hub key when it has the form F + digits, otherwise the local food id. The message "Published N foods." confirms the count. USDA foods are built in and are not published.

5.2 Preconditions

  1. The person is signed in with an admin account (otherwise the server refuses every write).
  2. The device's account database contains the Hub foods. On a signed-in device the Hub sync does not start automatically (only Firestore sync runs), but the sync card stays in Settings; the admin must connect it with the owner's connection code and press Import foods from sheet first. This sequence on a signed-in admin device is Not verified.
  3. Run the quality checklist (section 9) and the Hub check (section 4) first.

5.3 Steps

  1. Sign in as admin on the device that holds the current Hub foods.
  2. Settings → Hub sync card → Import foods from sheet; confirm the counts.
  3. Settings → account card → Administration → Publish verified foods.
  4. Note N from "Published N foods." in the owner's log.
  5. Check on a second, non-admin test account that a changed food shows the new values.

5.4 What happens on users' devices

Every signed-in device keeps a live listener on /foods. When the collection changes, all documents are merged into the local food list as source "sheet" (matched by key; changed values update the local copy). The merge never deletes local foods.

5.5 Cost

Each publish writes one document per food (≈ 160 writes for the current Hub) and every signed-in device re-reads the collection. This counts against the Firestore Spark daily limits (see MEGO_Monitoring_and_Maintenance). Publish only after real changes.

5.6 Caution: republishing approved suggestions

A device that received an approved suggestion (foods/U-…) holds it locally as a "sheet" food with key U-…. Because publishing uses the Hub key only when it looks like F####, pressing Publish on such a device writes that food a second time under its local id, creating a duplicate shared document. This follows from the code (publishSharedFoods) and has not been observed in production. The same applies to Hub foods whose id is not of the form F####, such as the LIB-ING-… and LIB-… rows added by --hub-complete-foods (3.1): they are published under each device's local id, so publishing them from two different devices creates two shared copies. Until it is fixed, publish from a single device whose sheet foods come from the Hub, or remove the duplicate afterwards in the Firebase console.

6. Procedure: reviewing user food suggestions

  1. A signed-in user presses "Suggest for the shared database" in the editor of one of their own foods; a foodSubmissions document with status: "pending" is created. Nothing is published automatically.
  2. Administration → Food submissions to review lists up to 100 pending items (name, state, kcal, P, C, F per 100 g, source reference, notes).
  3. Check the values against the label or another reliable source (section 9).
  4. Approve → copied to foods/U-<submissionId> with the note "user submission reviewed by admin"; the submission becomes approved. Reject → only marked rejected.

Values cannot be edited in the dashboard, and the submitter is not notified in the app.

7. Removing or correcting a shared food

  • Correct: fix the value in the Hub and republish (section 5) — the document with the same F#### id is overwritten and devices update their copy.
  • Remove: there is no unpublish button. The owner can delete the document in the Firebase console, but devices that already received it keep their local copy, because the listener merges and never deletes. To neutralise a wrong food on all devices, publish corrected values instead of deleting.
  • An approved suggestion with wrong values can be corrected only in the console (foods/U-…); Not verified.

8. The built-in USDA reference database

Built by node scripts/build-food-db.mjs <directory with the unzipped USDA CSV folders> from USDA FoodData Central (public domain): SR Legacy (2018-04) and FNDDS (2024-10-31). Values are copied exactly per 100 g edible portion; foods without a published energy value are skipped; each row keeps its FDC ID; Atwater mismatches are flagged, not changed. Output: public/fooddb/usda.json and public/fooddb/usda-extra.json. A rebuilt file reaches users only through a normal release (commit → GitHub Actions tests → deploy; see MEGO_Build_and_Release_Procedures). Administrators cannot change USDA values in the app.
