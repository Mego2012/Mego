الغرض والنطاق

تحدد هذه الوثيقة ما يجب مراقبته في نظام MEGO العامل، والأدوات المتاحة لذلك، ومهام الصيانة الدورية وأوامرها. لا يملك MEGO أي خدمة مراقبة أو تنبيه آلية؛ فكل فحص أدناه يبدؤه شخص (أو يعمل ضمن عملية النشر). تغطي الوثيقة النشر على GitHub Pages، ومشروع Firebase (خطة Spark المجانية)، وخادم Apps Script والـ Hub، وماسح الوجبات Gemini. المصادر: .github/workflows/deploy.yml وscripts/laptop-setup.mjs وscripts/live-verify.mjs وapps-script/Code.gs وsrc/lib/firebase.ts وsrc/lib/cloudSync.ts وdocs/ARCHITECTURE.md.

لا تلصق أبدًا رابط الخادم /exec أو توكن التطبيق أو مفتاح Gemini أو رمز الاتصال في التذاكر أو المحادثات أو لقطات الشاشة. حالة الإعداد (معرّف السكربت والرابط والتوكن) محفوظة على حاسوب المالك في ~/.mego-backend/.

2. عمليات النشر (GitHub Actions)

يعمل سير العمل .github/workflows/deploy.yml عند كل دفع (push) إلى main أو claude/nutrition-tracking-app-989rku، ويمكن تشغيله يدويًا (workflow_dispatch).

 push ─► build job: checkout → Node 22 → npm ci → npm test (vitest) → npm run build ─► upload dist
                                                   │ fails?
                                                   └─► stop: the live site keeps the previous version
         deploy job (needs build) ─► actions/deploy-pages ─► https://mego2012.github.io/Mego/
  • لا تعمل في هذا المسار إلا اختبارات الوحدات (npm test: ‏195 اختبارًا في 13 ملفًا حتى 10 نوفمبر 2026). أما اختبارات المتصفح واللمس وتعدد المستخدمين والقواعد والاختبارات الحية فتُشغَّل يدويًا.
  • مجموعة التزامن pages مع cancel-in-progress: الدفع الأحدث يلغي تشغيلًا أقدم ما زال قيد التنفيذ.
  • طريقة الفحص: المستودع على GitHub ← تبويب Actions ← آخر تشغيل باللون الأخضر؛ أو gh run list --workflow deploy.yml --limit 5.
  • عند الفشل: افتح سجل الخطوة الفاشلة، أصلح ثم ادفع مجددًا. لا يتغير شيء في الموقع الحي حتى ينجح تشغيل.

3. التحقق الحي من تطبيق الإنتاج

يفتح scripts/live-verify.mjs التطبيق المنشور في متصفح حقيقي (Playwright) مقابل مشروع Firebase الحقيقي، وينشئ حسابين مؤقتين بعناوين عشوائية على example.com ويحذفهما في النهاية حتى عند فشل أحد الفحوص. ولا يستخدم إلا توكنات حسابي الاختبار، فكل نتيجة «مسموح/مرفوض» هي قواعد الإنتاج نفسها وهي تعمل.

  • التشغيل: node scripts/live-verify.mjs (أو node scripts/laptop-setup.mjs --verify). يجب تثبيت Playwright (npm install --no-save playwright@1.63.0 && npx playwright install chromium).
  • التقرير: ~/.mego-backend/live-verify-<time>.md.
  • يحتوي السكربت الآن 17 فحصًا: تقديم الموقع والإعدادات، وتسجيل حسابين، وقراءة كل مستخدم لبطاقته فقط، وتسجيل الطعام ومزامنته، والعزل على الخادم، وتغذية الوصفات لحساب جديد، وخصوصية الكارديو والتمارين، والمزامنة إلى جهاز ثانٍ، والتقرير الأسبوعي والشهري، ورفض وظائف المسؤول لحساب عادي، وطلب استعادة كلمة المرور، والخروج والدخول، وحذف الحسابين.
  • آخر نتيجة مسجلة على الإنتاج: 14/14 في 7 نوفمبر 2026 بمجموعة الفحوص السابقة. أما تشغيل كامل على الإنتاج يشمل الفحوص الثلاثة المضافة لاحقًا (الوصفات والكارديو والتمارين) فهو غير مُتحقَّق منه في سجلات المستودع.

كل تشغيل ينشئ حسابات ويحذفها، فيستهلك بضع عشرات من عمليات القراءة والكتابة في Firestore وعمليتي تسجيل؛ ولا يمس المستخدمين الحقيقيين.

4. سلامة الخادم والـ Hub

الأمر node scripts/laptop-setup.mjs --test يشغّل الاختبارات الحية على الخادم الحالي دون إعادة نشر:

  1. الخادم يستجيب بتوكن المالك، والتوكن الخاطئ يُرفض؛
  2. هوية الـ Hub (المصدر هو ملف Excel الأصلي)، وأن الـ Hub جدول Google أصلي قابل للكتابة، وتحقق installMego؛
  3. Food_Database يضم كل الأطعمة بقيم مقروءة؛
  4. كتابة سجل اختبار من الهاتف إلى الـ Hub وقراءته، وأن النسخة الأقدم لا تستبدل الأحدث، والحذف المرن إلى Deleted_Records؛
  5. Gemini: وجود المفتاح ثم تحليل صورة حقيقية واحدة (صورة وجبة عامة من Wikimedia Commons، أو --photo <file>).

ملاحظة: يترك الاختبار صفًا محذوفًا حذفًا مرنًا في Deleted_Records، وإذا نجح التحليل يُحتسب مسحًا واحدًا في عداد الذكاء الاصطناعي اليومي. ويُكتب تقرير في ~/.mego-backend/report-<time>.md.

فحص سريع للإصدار دون توكن: طلب GET على رابط تطبيق الويب يعيد { ok: true, app: "mego-nutrition", version: N } (SCRIPT_VERSION). الشيفرة في المستودع عند الإصدار 8 (الإصدار 7 = تحويل أخطاء الذكاء الاصطناعي وسلسلة النماذج، 10 نوفمبر 2026؛ والإصدار 8 = الإجراء fillFoodNames لإكمال أطعمة الـ Hub). الإصدار 7 مُتحقَّق منه حيًّا، أما نشر الإصدار 8 على خادم المالك فـغير مُتحقَّق منه. وإن ظهر رقم أقل من رقم المستودع فعلى المالك تشغيل --update-backend.

5. مراقبة ماسح الذكاء الاصطناعي: aiDiag وaiStats والعدادات

5.1 aiDiag — سلامة كل نموذج

شغّل git pull && node scripts/laptop-setup.mjs --update-backend. يرفع الأمر Code.gs الحالي إلى النشر نفسه (الرابط نفسه، والبيانات دون مساس) ثم يستدعي aiDiag الذي يرسل طلبًا نصيًا صغيرًا جدًا («Reply with the single word OK.») إلى كل نموذج مجاني، ويطبع لكل نموذج: حالة HTTP، ورمز الخطأ المحوَّل، وحالة Google ورسالتها، والمدة بالمللي ثانية.

  backend version 7 · configured model gemini-3.8-flash
  ✅ gemini-3.8-flash: HTTP 200 OK (… ms)
  ❌ gemini-3.6-flash: HTTP 503 AI_OVERLOADED — UNAVAILABLE: … (… ms)   ← example of a failing model
  ✅ gemini-3.5-flash-lite: HTTP 200 OK (… ms)

(الشكل توضيحي؛ القيم تعتمد على Google وقت التشغيل.) ويمكن أيضًا استدعاء aiDiag بتوكن هوية Firebase لأي مستخدم مسجَّل له بطاقة — لا للمسؤولين فقط — ولا يستهلك عدادات المسح.

5.2 aiStats — الاستخدام خلال آخر 7 أيام (للمسؤول فقط)

يتحقق إجراء الخادم aiStats من توكن هوية Firebase للمستدعي ومن وجود admins/{uid}، ثم يعيد: النموذج، وهل المفتاح مضبوط، والحدين اليوميين العام ولكل مستخدم، ولكل يوم من آخر 7 أيام عدد عمليات المسح الناجحة وعدد المستخدمين المختلفين؛ أعدادًا فقط دون أي محتوى. لا توجد شاشة في التطبيق تستدعيه بعد، لذلك تُقرأ الأرقام اليوم مباشرة من محرر Apps Script ← Project settings ← Script Properties (المفاتيح AI_USED_<yyyy-mm-dd> وAI_U_<yyyy-mm-dd>_<uid>). لا تلتقط صورة لتلك الصفحة أبدًا، فهي تحتوي أيضًا مفتاح Gemini وتوكن التطبيق.

العدادات القديمة: الدالة cleanupAiCounters() تحذف العدادات الأقدم من 8 أيام، وهي مصممة لمشغّل زمني يومي اختياري لا يثبّته سكربت الإعداد؛ ويستطيع المالك إضافته من محرر Apps Script (Triggers ← إضافة مشغّل ← cleanupAiCounters، زمني، يومي). غير مُتحقَّق منه.

6. لوحة الإدارة وتقارير الأخطاء

عند وجود مسؤول (لا يوجد بعد) تعرض #/admin عدد المسجلين والنشطين خلال 7 أيام والحسابات الموقوفة والأطعمة المقترحة المعلّقة، إضافة إلى آخر 50 تقرير خطأ. تُنشأ تقارير الأخطاء تلقائيًا من الأجهزة المسجَّلة بنوع sync (فشل رفع إلى السحابة) أو sync-apply (تعذّر تطبيق سجل واحد منزَّل؛ وتذكر الرسالة الجدول والمفتاح). ازدياد التقارير بعد إصدار جديد إشارة إلى ضرورة التحقيق (انظر MEGO_Support_and_Incident_Management). التقارير لا تحمل معرّف المستخدم.

7. حدود الخطط المجانية

تعمل كل الخدمات على خطط مجانية؛ وعند بلوغ الحد تتوقف الخدمة لبقية اليوم بدل أي فوترة. الأرقام أدناه كما وردت في docs/ARCHITECTURE.md، وقد تغيّرها Google؛ راجع وثائق Firebase وGemini الحالية (غير مُتحقَّق منها مقابل صفحات Google في 10 نوفمبر 2026).

الخدمةالحدما يستهلكه في MEGO
Firebase Authentication (Spark)3,000 مستخدم نشط يوميًا؛ 150 رسالة استعادة كلمة مرور يوميًا؛ 100 تسجيل في الساعة لكل عنوان IPالدخول والتسجيل وطلبات الاستعادة وتشغيلات live-verify
Cloud Firestore (Spark)1 GiB تخزين؛ 50,000 قراءة و20,000 كتابة و20,000 حذف يوميًامستمعات حية على 12 جدولًا خاصًا إضافة إلى /foods لكل جهاز مسجَّل؛ كل تغيير محلي = كتابة واحدة؛ نشر الأطعمة = كتابة لكل طعام وإعادة قراءة على كل جهاز؛ حذف الحساب = حذف لكل سجل

أين تنظر: وحدة تحكم Firebase ← المشروع ← صفحات الاستخدام (Usage) لـ Firestore؛ وGoogle AI Studio لاستخدام Gemini. أسماء القوائم الدقيقة غير مُتحقَّق منها.
