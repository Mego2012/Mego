Purpose and scope

This document lists what must be watched in the running MEGO system, the tools available for watching it, and the routine maintenance tasks with their commands. MEGO has no automated monitoring or alerting service: every check below is started by a person (or runs as part of a deployment). The document covers the GitHub Pages deployment, the Firebase project (Spark plan), the Apps Script backend and Hub, and the Gemini meal scanner. Sources: .github/workflows/deploy.yml, scripts/laptop-setup.mjs, scripts/live-verify.mjs, apps-script/Code.gs, src/lib/firebase.ts, src/lib/cloudSync.ts, docs/ARCHITECTURE.md.

Never paste the backend /exec URL, the app token, the Gemini key or a connection code into tickets, chats or screenshots. The setup state (script id, URL, token) is kept on the owner's laptop in ~/.mego-backend/.

2. Deployment runs (GitHub Actions)

The workflow .github/workflows/deploy.yml runs on every push to main or claude/nutrition-tracking-app-989rku and can be started manually (workflow_dispatch).

 push ─► build job: checkout → Node 22 → npm ci → npm test (vitest) → npm run build ─► upload dist
                                                   │ fails?
                                                   └─► stop: the live site keeps the previous version
         deploy job (needs build) ─► actions/deploy-pages ─► https://mego2012.github.io/Mego/
  • Only the unit tests (npm test, 195 tests in 13 files as of 10 Nov 2026) run in the pipeline. Browser, touch, multi-user, rules and live suites are run separately by hand.
  • Concurrency group pages with cancel-in-progress: a newer push cancels an older run still in progress.
  • How to check: GitHub repository → Actions tab → latest run is green; or gh run list --workflow deploy.yml --limit 5.
  • If a run fails: open the failing step log; fix and push again. Nothing on the live site changes until a run succeeds.

3. Live verification of the production app

scripts/live-verify.mjs opens the deployed app in a real browser (Playwright) against the real Firebase project, creates two disposable accounts with random addresses on example.com, and deletes both at the end, also when a check fails. It uses only the test accounts' own tokens, so every allowed/denied result is the production rules at work.

  • Run: node scripts/live-verify.mjs (or node scripts/laptop-setup.mjs --verify). Playwright must be installed (npm install --no-save playwright@1.63.0 && npx playwright install chromium).
  • Report: ~/.mego-backend/live-verify-<time>.md.
  • The script now contains 17 checks: site and config served, registration of two accounts, own profile only, food logging and sync, server-side isolation, recipe nutrition for a new account, cardio and workout privacy, second-device sync, weekly and monthly report, admin functions refused for a regular account, password-reset request, sign-out/in, deletion of both accounts.
  • Last recorded production result: 14/14 on 7 Nov 2026 with the earlier set of checks. A full production run with the three checks added later (recipe, cardio, workouts) is Not verified in the repository records.

Each run creates and deletes accounts, so it uses a few dozen Firestore reads/writes and two sign-ups; it does not affect real users.

4. Backend and Hub health

node scripts/laptop-setup.mjs --test runs the live integration tests against the existing backend without redeploying:

  1. backend answers with the owner token; a wrong token is refused;
  2. Hub identity (source is the original Excel file) and Hub is a native, writable Google Sheet; installMego verification;
  3. Food_Database has every food with readable values;
  4. write phone → Hub of a test record, read back, an older copy never overwrites a newer one, soft delete into Deleted_Records;
  5. Gemini: key present, then one real photo analysis (a public Wikimedia Commons meal photo, or --photo <file>).

Note: the test leaves a soft-deleted row in Deleted_Records and, if the analysis succeeds, counts one scan in the daily AI counter. A report is written to ~/.mego-backend/report-<time>.md.

Quick version check without the token: an HTTP GET on the web-app URL returns { ok: true, app: "mego-nutrition", version: N } (SCRIPT_VERSION). The repository code is at version 8 (v7 = AI error mapping and model chain, 10 Nov 2026; v8 = action fillFoodNames for the Hub food completion). Version 7 was verified live; whether v8 has been deployed to the owner's backend is Not verified. A lower number than the repository means the owner should run --update-backend.

5. AI scanner monitoring: aiDiag, aiStats and counters

5.1 aiDiag — per-model health

Run git pull && node scripts/laptop-setup.mjs --update-backend. It uploads the current Code.gs to the same deployment (same URL, data untouched) and then calls aiDiag, which sends one tiny text-only request ("Reply with the single word OK.") to each free model and prints, per model: HTTP status, mapped error code, Google's status/message and duration in ms.

  backend version 7 · configured model gemini-3.8-flash
  ✅ gemini-3.8-flash: HTTP 200 OK (… ms)
  ❌ gemini-3.6-flash: HTTP 503 AI_OVERLOADED — UNAVAILABLE: … (… ms)   ← example of a failing model
  ✅ gemini-3.5-flash-lite: HTTP 200 OK (… ms)

(Illustrative layout; the values depend on Google at the time of the run.) aiDiag is also reachable with a Firebase ID token for any signed-in user who has a profile — not only admins; it does not use the scan counters.

5.2 aiStats — usage for the last 7 days (admin only)

The backend action aiStats checks the caller's Firebase ID token and that admins/{uid} exists, then returns: model, whether a key is configured, global and per-user daily limits, and for each of the last 7 days the number of successful scans and of distinct users. It returns counts only, no content. No screen in the app calls it yet, so today the figures are read directly in the Apps Script editor → Project settings → Script Properties (keys AI_USED_<yyyy-mm-dd> and AI_U_<yyyy-mm-dd>_<uid>). Never screenshot that page: it also holds the Gemini key and the app token.

6. Admin dashboard and error reports

Once an admin exists (none yet), #/admin shows registered users, active in 7 days, suspended accounts and pending food submissions, plus the latest 50 error reports. Error reports are created automatically by signed-in devices with kind sync (a cloud push failed) or sync-apply (one downloaded record could not be applied; the message names table/key). A rising number of reports after a release is a signal to investigate (see MEGO_Support_and_Incident_Management). Reports carry no user id.

7. Free-plan limits

All services run on free plans; when a limit is reached the service stops for the day instead of billing. The figures below are as documented in docs/ARCHITECTURE.md; Google can change them — check the current Firebase and Gemini documentation (Not verified against Google's pages on 10 Nov 2026).

ServiceLimitWhat in MEGO consumes it
Firebase Authentication (Spark)3,000 daily active users; 150 password-reset e-mails/day; 100 sign-ups/hour per IPSign-ins, registrations, reset requests, live-verify runs
Cloud Firestore (Spark)1 GiB stored; 50,000 reads, 20,000 writes, 20,000 deletes per dayLive listeners on 12 private tables plus /foods per signed-in device; each local change = 1 write; publishing foods = 1 write per food and a re-read on every device; account deletion = 1 delete per record
Gemini API free tierGoogle's per-minute and per-day quotasEach meal scan (plus up to two fallback models on failure); aiDiag = 3 small requests
Google Apps ScriptGoogle's consumer quotas (Not verified)Hub sync, scans, Drive backups

Where to look: Firebase console → project → Usage and billing / Firestore usage; Google AI Studio for Gemini usage. Exact menu names are Not verified.
