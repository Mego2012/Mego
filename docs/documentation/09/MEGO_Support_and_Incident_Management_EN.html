Purpose and scope

This document defines how user problems are received and answered, and how incidents (faults that affect users' data or a whole feature) are classified, investigated, fixed, verified and recorded. It includes two real incidents from 10 November 2026 as worked examples. No personal data is included: the incidents are described by symptom and mechanism only.

Current reality: MEGO has no support desk, ticket system or in-app contact form, and the published privacy page still contains the placeholder for the operator's contact address. Support is therefore handled directly by the Project Owner. The severity levels and response steps below are a proposed process for the owner to approve; they are not enforced by any tool.

  report,    scope)    data,      find root      + tests) emulator, should do)   lessons,
  monitor)             no wipes)  cause)                 live)                  follow-ups)
  • Contain never means deleting data. Prefer leaving cloud records untouched and taking a local backup before any import.
  • Fix always includes an automated test that reproduces the fault, so it cannot come back unnoticed.
  • Verify on the level that matches the fault: unit test, emulator scenario, then the live site.

4. First-line triage checklist

  1. Guest or signed-in account? (Guest data exists only on that device.)
  2. Which device and browser; installed as an app or in the browser tab?
  3. Exact message on screen (an AI error shows a code such as "AI overloaded" plus Google's text).
  4. Online? The sync status in Settings shows idle / syncing / offline / error and the pending count.
  5. Settings → Data check (read-only): record counts compared with the pre-update backup, suspect per-serving foods, possible duplicates.
  6. Settings → local backups: is there a recent automatic or pre-update backup on this device?
  7. Has a release gone out recently? Check the GitHub Actions history.
  8. Is it reproducible on another device or a disposable test account?

Never ask a user for their password, and never ask them to send the Hub connection code or screenshots of Script Properties.

6. Worked example A: "AI is busy" (10 Nov 2026)

StageDetails
SymptomEvery meal-photo analysis in the live app ended with "The AI service is busy right now. Please try again in a minute." Severity: SEV-2 (feature unusable for everyone; manual logging still worked).
InvestigationReproduced live with a disposable account: every analysis — even a 96-pixel image — returned the busy error after 4–30 s. So the image size was not the cause: Google answered with 5xx server errors. Reading the backend showed that it mapped every 5xx answer to one generic "busy" code, never retried, and still counted each failure against the user's daily scans.
Root causeGoogle's 503 "overloaded" answer on the primary free model (gemini-3.8-flash), reported by the old backend as "busy" without retry or fallback.
Fix (backend v6)Precise error codes with Google's status/message (never the key): AI_OVERLOADED 503, AI_SERVER_ERROR 500, AI_TIMEOUT 504, quota, key, region, model, image, config; retries after 2 s and 4 s for temporary errors; fallback through the free models gemini-3.8-flash → gemini-3.6-flash → gemini-3.5-flash-lite (free tier only, never a paid model); failed requests no longer counted; new aiDiag action. App: automatic retry after 3 s and 8 s for temporary errors only, manual retry keeps the photo, one request at a time, image validation and compression, bilingual messages. Setup: --update-backend (same URL, data untouched).
Follow-up fix (backend v7)A live check after v6 showed the primary model answering 503 three times in a row on every attempt, so a photo took 60–200 s before the fallback answered. v7 moves on to the next free model immediately after a 503.
Verification9 new unit tests for the scanner (later extended); live on 10 Nov 2026 a real meal photo was analysed through the live app UI (disposable account) in ≈ 64 s with 4 items recognised.
Residual riskThe free tier remains slow at peak times; overload can still occur on all three models at once.
Owner actiongit pull && node scripts/laptop-setup.mjs --update-backend; when users report AI problems, read the aiDiag output first.

7. Worked example B: data missing after browser storage loss (10 Nov 2026)

StageDetails
SymptomOn an Android phone with a signed-in account, the app suddenly showed the welcome screen. After signing in again with the same account, the diary was empty and the calorie target showed the default 2000. It had happened once before; that time the data was entered again by hand. Severity: SEV-1 (data appeared lost).
InvestigationThe browser had lost its IndexedDB (the local records and the Firebase session) while localStorage survived. The cloud still held all records. The fault was reproduced on the Firebase emulators with a new scenario e2e/storage-loss.mjs.
Root causeTwo defects: (1) the cloud listener started each table from a "last seen" marker kept in localStorage; the marker survived, so the older records were never downloaded into the new, empty database; (2) a fresh default settings record got updatedAt = now and therefore outranked the account's saved settings.
FixIn src/lib/cloudSync.ts, account.ts, repo.ts: markers renamed to mego.cloud2. so every device re-downloads its account once; a missing local database resets the markers; an empty table always downloads in full; settings are always re-read; untouched defaults (updatedAt 0) never outrank the cloud copy. Second commit: one record that cannot be applied no longer stops the download (it is reported as sync-apply); two weigh-ins for the same date keep the newer one on the device while the other stays in the cloud; Data check lists possible duplicates (re-entered copies) read-only. All changes are non-destructive: newer local copies are kept.
VerificationUnit tests (tests/cloud-recovery.test.ts); emulator scenario e2e/storage-loss.mjs including old and re-entered copies; deployed live; the owner confirmed the data came back.
Residual riskThe browser can still clear storage; signed-in data is safe in the cloud, guest data is not. Re-entered duplicates from the first loss remain until the user removes them.
Lesson for usersSigned-in accounts are recovered by signing in again. Guest data lives only on the device — export regularly or create an account.

8. Rules during every incident

  • Do not delete or overwrite cloud data to "clean up"; investigate first.
  • Take a local backup on the affected device before any import or restore.
  • Use disposable test accounts for reproduction, never a user's account.
  • No personal data in incident records, commits or reports: no names, e-mail addresses, diary content or uids of real users.
  • Never expose secrets (Gemini key, app token, /exec URL, connection code) in logs or screenshots. If one is exposed, rotate it (MEGO_Monitoring_and_Maintenance section 8).
  • Every fix ships with a test and through the normal deploy workflow.
