Purpose and scope

This document defines the step-by-step procedures for managing MEGO user accounts over their whole life cycle: creating the first administrator, reviewing accounts, suspending and reactivating them, handling password problems and processing account deletion. It explains which actions are self-service for the user, which are done by an administrator in the in-app dashboard (#/admin) and which can only be done by the Project Owner in the Firebase console. All behaviour described is taken from src/pages/Account.tsx, src/lib/firebase.ts, src/lib/account.ts, firebase/firestore.rules, apps-script/Code.gs and scripts/laptop-setup.mjs.

Status note (10 November 2026): no administrator account exists yet. The owner must first register a normal account in the live app and then run node scripts/laptop-setup.mjs --cloud <e-mail> (section 2). Until then, the administrator procedures in sections 4–6 cannot be carried out in production.

Guest users (no sign-in) are outside the scope of user management: their data exists only in the browser database mego-nutrition on their own device and is invisible to administrators and to the cloud.

2. Prerequisite: creating the first administrator

The admin role cannot be requested or granted inside the app. Procedure (owner only):

  1. Open the live app https://mego2012.github.io/Mego/ and register a normal account (3-step registration) with the e-mail address that should become administrator.
  2. On the owner's laptop, in the repository folder, run node scripts/laptop-setup.mjs --cloud <that e-mail>.
  3. The script looks the e-mail up in Firebase Authentication. If no account is found it prints "has no account yet: register in the app, then run again" and writes nothing.
  4. If found, it writes admins/{uid} with the owner's Google credentials and reports "administrator role for <e-mail>" with ✅ or ❌.
  5. Sign out and in again (or reload). The Administration button appears in the account card in Settings.

To remove an administrator there is no script flag and no in-app button: the owner deletes the document admins/{uid} in the Firebase console (Firestore → Data). Not verified in production.

3. Account life cycle

 [Guest]──register (3 steps)──►[ACTIVE]──admin: Suspend──►[SUSPENDED]
                                  ▲                           │
                                  └────admin: Reactivate──────┘
 [ACTIVE]──user: Delete account (password)──►[DELETED]
 [SUSPENDED]──cannot delete from the app (see 8.3)

At registration the app creates the Firebase login and the profile with status: "active"; the rules only accept a new profile whose status is active, whose ageConfirmed is true and whose e-mail equals the e-mail of the signed-in login. Administrators never create accounts.

4. Procedure: reviewing accounts

  1. Sign in with the admin account → Settings → account card → Administration (or open #/admin).
  2. Read the KPI tiles: registered users (all profiles), active in the last 7 days (lastActiveAt ≥ now − 7 days), suspended, food submissions pending. The bar shows round(active7d ÷ total × 100) %.
  3. Scroll the Accounts card: the newest 100 profiles (ordered by createdAt descending), each with name, e-mail, country, registration date, last-active date and a status chip.

Limitations: no search, filter or paging. Accounts beyond the newest 100 are not listed in the dashboard; they can only be found in the Firebase console.

5. Procedure: suspending an account

5.1 When to suspend

Suspension is the only enforcement tool available in the app. The project has no approved policy yet that lists suspension grounds; the draft Acceptable Use Policy (MEGO_Acceptable_Use_Policy) is the intended reference once approved. Until then, the owner decides case by case and records the decision (section 11).

5.2 Steps

  1. In the Accounts card find the row and press Suspend. (The button is hidden on the administrator's own row.)
  2. The app writes status: "suspended" to profiles/{uid}; the list and tiles reload and "Saved" is shown.
  3. Record the action (date, uid, reason) in the owner's log.

5.3 Effect

AreaEffect of suspension
Private cloud dataKept unchanged. Every read and write under users/{uid} is refused by the server (isActive() is false)
App screenAt the next start the app shows "Account suspended — This account has been suspended by the administrator. Your data is kept and nothing has been deleted." with only a Sign-out button; cloud sync is not started

AI meal scannerThe Apps Script proxy reads the profile with the user's own token and answers unauthorized when the status is not active
Firebase loginNot disabled — the user can still sign in, but sees only the suspended screen
Profile cardThe user cannot change name/country while suspended (owner update requires status active)

6. Procedure: reactivating an account

  1. In the Accounts card find the row with the "Suspended" chip and press Reactivate.
  2. status returns to active. The user regains access the next time the app starts (reload or sign in again); private data was never touched.
  3. Record the action in the owner's log.

7. Procedure: password problems

Password reset is self-service only. On the sign-in screen the user chooses the reset option and enters the e-mail; the app calls Firebase sendPasswordResetEmail. Firebase sends the reset message. Administrators cannot see, set or reset passwords.

  • If the user receives no message: ask them to check spam and the spelling of the address, and try again later. The Firebase Spark plan limits password-reset e-mails (150 per day according to docs/ARCHITECTURE.md).
  • Live status: the reset request was accepted by Firebase (HTTP 200) in the live verification; delivery to an inbox is not verified.

8. Procedure: account deletion

8.1 Self-service deletion (normal case)

  1. The user exports their data first if they want to keep it (Settings → backup/export; see MEGO_Backup_and_Export_Guide).
  2. Settings → account card → Delete account. The warning reads: "This permanently deletes your account, your cloud data and this device's copy of it."
  3. The user enters the password and confirms Delete permanently.

What the app then does, in this order (deleteMyAccount):

  1. Re-authenticates with the password (Google requires a recent sign-in) — nothing is removed if the password is wrong.
  2. Deletes every document in every synced table under users/{uid}.
  3. Deletes profiles/{uid}.
  4. Deletes the Firebase login.
  5. Deletes the local database mego-u-<uid> on this device and returns to the start screen.

8.3 Suspended users

A suspended user cannot complete deletion in the app: the suspended screen offers only Sign-out, and the server refuses reads of users/{uid}, which the deletion needs. Procedure: reactivate the account (section 6), let the user delete it, or — if the user cannot or will not sign in — the owner deletes the data in the Firebase console (see 9). The console path is Not verified.

8.4 Deletion request from a user who cannot sign in

There is no in-app request form and no published contact address yet (the privacy policy contains the placeholder "[Operator name, country and contact email — to be completed by the owner before launch.]"). Until a contact exists, such requests cannot be received through the product. Before acting on any request received outside the app, the owner must confirm that it comes from the holder of the account e-mail. The verification method is not defined yet (Not verified).

10. Requests that cannot be fulfilled

  • "Show me a user's diary / weight / photos" — admins have no access (rules); progress photos are never uploaded.
  • "Change a user's name, e-mail or country" — admins may change only status; the user changes name/country in the account card. Changing the login e-mail is not offered in the app.
  • "Reset my password for me" — self-service only (section 7).
  • "Recover my guest data" — guest data exists only on the device; if the browser storage was cleared it cannot be restored from the cloud (local backups on the same device may help).

11. Record keeping

The app keeps no audit log of admin actions (the profile stores only the current status). Recommended practice for the owner: keep a private log with date, uid (not the e-mail), action (suspend / reactivate / grant / remove admin / console deletion), reason and who decided. Do not store diary content or other personal records in this log.
