Purpose and scope

This manual lists the problems that can occur when using MEGO (the nutrition-tracking web app at https://mego2012.github.io/Mego/), explains their real causes as implemented in the code, and gives step-by-step fixes. It covers signing in, missing data after a browser storage loss (including the incident of 10 November 2026), cloud sync, the AI meal scanner (including the "AI is busy" message), barcode lookup, the Data check and owner backend errors. It does not cover development or deployment problems (see MEGO_Developer_Setup_and_Local_Installation and MEGO_Production_Deployment_Guide).

1. First checks for any problem

  1. Connection. When the phone is offline the app shows "You are offline. Everything you log is saved and will sync when you reconnect." Logging still works; sync, sign-in, barcode lookup and the AI scanner need the internet.
  2. Reload the app (close it completely and open it again).
  3. Are you signed in or a guest? Open the Account screen. A guest sees "You are using MEGO without an account: data stays on this device only." This matters for recovery (section 3).
  4. Before trying anything risky, export your data (Account → "Export my data", or Settings → "Download backup file").

3. Data missing after signing in again (storage loss) — incident of 10 Nov 2026

3.1 Symptoms

  • The app suddenly opens on the welcome screen although you were signed in.
  • After signing in again the diary, foods and targets look empty, or the default calorie target is shown instead of yours.

3.2 What happened

On 10 November 2026 an Android phone lost its browser database (IndexedDB: all local records and the Firebase session) while the browser's small key-value storage (localStorage) survived. It had happened once before on the same kind of device. The cloud copy of the account was intact, but the old app version did not download it again because:

  1. The cloud listener started from "last seen" markers kept in localStorage. These markers survived, so the app asked only for records newer than the marker — the older records were never requested again.
  2. A fresh default settings record created on the empty device was treated as newer than the saved settings in the cloud, so the default targets won.
 Phone storage                       Cloud (Firestore)
 ┌───────────────────────────┐       ┌──────────────────────┐
 │ IndexedDB  ── LOST ──     │       │ all records: intact  │
 │ localStorage: markers OK  │──────▶│ "send only newer     │
 └───────────────────────────┘       │  than marker" → none │
                                     └──────────────────────┘

3.3 The fix (live since 10 Nov 2026)

Changed in src/lib/cloudSync.ts, src/lib/account.ts and src/lib/repo.ts:

  • Markers were renamed (mego.cloud2.), so every device re-downloads its account in full once.
  • If the local database of the account does not exist at sign-in, all markers of that account are reset.
  • An empty local table always downloads in full, whatever the marker says.
  • Settings (one document) are always re-read from the cloud.
  • Untouched default settings (updatedAt 0, identical to the defaults) never outrank the cloud copy.
  • One unreadable record no longer stops the download of the others.
  • When two weigh-ins exist for the same date (e.g. entered again after a loss), the newer one is shown on the device; the other stays in the cloud.

Nothing local is overwritten by the download: a newer local copy is kept and pushed to the cloud.

Open the Diary on a day you know had entries, and Settings → targets, to confirm. 5. Prevention: use an account if your data matters; download a backup file regularly; do not clear site data for the app. The app also asks the browser for persistent storage at start (navigator.storage.persist()); whether the browser grants it is up to the browser.

4. Cloud sync problems

  • "Offline — changes are saved on this device": changes wait in a local outbox and are sent when the connection returns.
  • A change seems to be ignored: the server refuses an update that is older than the copy already in the cloud. The newer copy then arrives on this device through the live listener. This is counted as a conflict, not an error.
  • Nothing syncs and the account is suspended: server rules allow reading and writing only while the account is active.
  • A record changed on another device does not appear: reopen the app while online; the listener downloads only changes newer than the last one seen, plus full downloads for empty tables (section 3.3).

5. AI meal scanner: "AI is busy" and other messages

5.1 Why "AI is busy" appeared

The scanner sends a reduced photo through the Apps Script backend to Google's Gemini API free tier. The root cause of the old generic message "The AI service is busy right now" was a Google 503 "overloaded" answer from the primary model, which the old backend reported as "busy" without retrying. It was not caused by the phone, the photo or the key.

5.2 What the current version does (backend SCRIPT_VERSION 7)

  • Google errors are mapped to precise codes and shown with Google's own status text ("Service response").
  • Free model chain: gemini-3.8-flash → gemini-3.6-flash → gemini-3.5-flash-lite. Only free-tier models; never a paid model.
  • 503 overloaded: moves at once to the next free model. 500 server error / 504 timeout: retried on the same model after 2 s and 4 s.
  • On the phone, temporary errors are retried automatically after 3 s and 8 s ("Retrying automatically (n/max)…"); the photo is kept so a manual Retry does not require choosing it again; only one request for the same photo runs at a time.
  • A failed analysis does not count against the user's daily scans.

6. Barcode scanning and Open Food Facts

  • No camera button / camera does not scan: camera scanning uses the browser's BarcodeDetector API (available in Chrome on Android). Otherwise type the barcode number manually.
  • "No product found for this barcode. Add it manually." Open Food Facts has no entry; create a custom food.
  • "Lookup failed (offline?). Add it manually." No connection or Open Food Facts not reachable.

7. Duplicates and suspicious values (Data check)

Settings → Data check → "Run check" is read-only ("nothing is changed"). It shows record counts compared with the latest pre-update backup, foods whose per-100 g values look like per-scoop values (e.g. a protein powder with fewer than 250 kcal per 100 g), and possible duplicate diary items and foods (for example entered again after a data loss). Delete extra copies yourself in the Diary.

9. When to escalate and what to report

Escalate to the project owner when data stays missing after section 3.4, when an error persists for more than a day, or when you suspect someone else accessed your account. Report: the date and time, the screen, the exact message (and "Service response" for the scanner), whether you are signed in or a guest, and the phone/browser. Never send passwords, keys, tokens or connection codes. Error reports collected by the app contain the error message only, without diary content. See MEGO_Support_and_Incident_Management.
