Purpose and scope

This document gives maintainers and future developers a reasoned list of technical and operational improvements: security follow-ups, data protection, testing and CI, AI scanner resilience, data quality, documentation, and the rules any future change should respect. Each recommendation states the observed fact, the risk or benefit, and a suggested action.

1. Principles to keep

Any future development should preserve the rules the current product is built on (verified in the code):

  • Zero cost: free tiers only; when a limit is reached the service stops instead of billing (no paid model, no billing account).
  • User's numbers first: nutrition always comes from the app's engine and the food database; AI and MET values are labelled estimates.
  • Nothing applied without consent: goals advisor, energy adjustment, training coach and meal scanner suggest; the user confirms.
  • No silent data loss: snapshots in diary entries, merge-only restore, older copies never overwrite newer, pre-update backup once per release.
  • Server-side isolation: firebase/firestore.rules restricts each user to their own records; admins never read private data.
  • No schema change without a backup: new data has been added to the synced kv table (Dexie schema still v2) rather than changing tables.

6. Free-tier capacity and monitoring

  • FD-40: Firebase Spark limits (e.g. 50,000 Firestore reads and 20,000 writes per day; 150 password-reset e-mails per day) bound how many active users MEGO can serve. Recommendation: before opening registration widely, review usage in the Firebase console; no capacity estimate has been made — Not verified.
  • FD-41: The app writes short error reports to the errorReports collection (no personal data; e.g. sync failures). Recommendation: once an admin exists, review them regularly from the admin dashboard.
  • FD-42: AI caps are AI_DAILY_LIMIT 40 and AI_USER_DAILY_LIMIT 10 (code defaults). Adjust them in Script Properties according to real usage, staying within Google's free quota.

7. Food data and content quality

  • FD-50: Use Settings → Data check (read-only) after each release to catch per-serving values entered as per-100 g, and possible duplicate entries.
  • FD-51: Recipe audit (docs/RECIPE-AUDIT.md): 100 of 101 recipes resolve from USDA references; "labneh" is unresolved and is never estimated; 6 recipes are flagged. Recommendation: add a verified labneh reference and re-run scripts/recipe-audit.mts.
  • FD-52: Food photos cover 74 foods; several common foods have no honestly matching freely licensed photo. Keep the rule "placeholder rather than a look-alike photo".
  • FD-53: Custom exercises have no illustration (built-in 54 are covered). Keep the muscle chart and the user's description as the fallback.

8. Platform, accessibility and performance

  • FD-60: Reminders fire only while the app is open or in the background (src/lib/reminders.ts). Reliable closed-app reminders need a push service; evaluate only free options.
  • FD-61: Accessibility features exist (focus styles, tap sizes, reduced motion) but no formal audit has been done. Recommend an audit of both Arabic RTL and English LTR screens.
  • FD-62: Heavy pages are lazy-loaded and charts are split into a separate chunk; no performance budget is measured. Recommend measuring start-up time on a mid-range Android phone.
  • FD-63: Minimum supported browser versions are not defined. Recommend stating them once real-device tests exist.

9. Documentation and code hygiene

  • FD-70: README.md still says "No workouts" and "60 built-in recipes"; the code has workouts and 101 recipes. docs/ARCHITECTURE.md states a global AI limit of 200/day; the code default is 40. Update these files so they match the official documentation set.
  • FD-71: Keep the rule that every new data type goes into the synced kv table or comes with a Dexie migration plus a pre-update backup and a restore test.
  • FD-72: Dependencies are pinned to exact versions in package.json. Review them periodically for security updates; no audit result is recorded — Not verified.
  • FD-73: When legal texts are finalised, update src/lib/i18n2.ts / i18n3.ts (placeholders and "Draft" labels) as listed in docs/LEGAL-REVIEW.md.
